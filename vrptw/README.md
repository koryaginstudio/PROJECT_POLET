# Стенд планировщика выездов

> **Устарело (пометка от 21 сентября).** Устройство движка и команды здесь верны. Разделы с результатами сняты
> на синтетике и прежнем коде — «расписание даёт вдвое больше
> алгоритма», «загрузка 0,41–0,61» (под этим файла замера нет); на
> данных заказчика числа другие.
>
> Что верно сейчас — `ФУНКЦИОНАЛЬНЫЕ-ТРЕБОВАНИЯ.md` и `README.md` в корне.

День монтажников на настоящей карте Москвы: адреса домов из
OpenStreetMap, дороги и время в пути из OSRM, симулятор исполнения с
каскадом опозданий и два планировщика на одном интерфейсе.

## Что нужно

Python 3.10 или новее, `numpy` и `scipy`. Больше ничего.

```bash
tar xzf vrptw_stend.tar.gz
cd <папка, где лежит vrptw/>
pip install numpy scipy
python3 -m vrptw.selfcheck
```

`selfcheck` проходит весь путь за полминуты: граф, генерация дня, оба
планировщика с проверкой инвариантов, симуляция, подбор смен, выгрузка для
интерфейса и проверка контракта. Если он зелёный — всё собрано правильно.

Команды запускаются **из папки, внутри которой лежит `vrptw/`**, а не из
самой `vrptw/`.

## Принцип

Планировщик видит только оценки (`est_minutes`, окна, SLA). Насколько
работа затянется, будет ли абонент дома, пустят ли в подъезд — живёт в
распределениях `WorkType` и **разыгрывается симулятором заново в каждом
прогоне**, а не записывается в заявку заранее. Иначе Монте-Карло меряет
одну лишь дорожную неопределённость.

Главная метрика — **покрытие дня**: доля выполненных из всех поступивших
заявок. Доля выполненных *из запланированных* выглядит внушительнее, но
почти не зависит от планировщика — её определяют неявки.

## Карта

Москва настоящая. Шестьсот адресов домов из OpenStreetMap по всем
пятидесяти районам, время в пути между ними — из маршрутизатора OSRM по
реальному графу дорог, линия на карте — настоящая ломаная по улицам.

Пробок OSRM не знает: он считает по свободной дороге. Поэтому почасовой
профиль пробок остался наш, и применяется он не одинаково ко всем
поездкам — от пары точек берётся то, насколько поездка меняет удаление от
центра. Едешь «внутрь» — поездка радиальная и встаёт сильнее, идёшь по
дуге на том же радиусе — кольцевая. Сверка с прежней выдуманной моделью:

| маршрут | км по дорогам | 13:00 | 18:00 |
|---|---|---|---|
| Митино → Марьино | 44,3 | 55 мин | 97 мин |
| Ясенево → Медведково | 50,9 | 51 мин | 92 мин |
| Хамовники → Таганский | 8,9 | 19 мин | 36 мин |

Проверить самому: `python3 -m vrptw.core.osm check` покажет те же
поездки на обеих сетях рядом.

**Интернет не нужен.** Адреса, матрица времени и геометрия маршрутов
лежат в репозитории и весят два с половиной мегабайта. Пересобрать их
можно (`python3 -m vrptw.core.osm fetch`), но на защите это не
понадобится.

Синтетическая радиально-кольцевая модель никуда не делась и осталась
запасным вариантом: ей не нужны ни файлы, ни сеть. Включается
переменной `VRPTW_SYNTHETIC_MAP=1`. Все числа ниже сняты на настоящей
карте.

## Запуск

Время указано для двух ядер; на нормальном ноутбуке будет заметно быстрее.

| Команда | Время | Что покажет |
|---|---|---|
| `python3 -m vrptw.selfcheck` | 40 с | всё ли собрано правильно |
| `python3 -m vrptw.core.validate_day` | мгновенно | годен ли день к планированию |
| `python3 -m vrptw.core.osm points дома.json` | минуты | сеть под настоящие адреса |
| `python3 -m vrptw.diagnose` | 1 мин | во что упирается день |
| `python3 -m vrptw.bench 12` | 3 мин | парное сравнение планировщиков |
| `python3 -m vrptw.shiftbench proxy` | 2 мин | можно ли верить прокси спроса |
| `python3 -m vrptw.validate` | 8 мин | held-out, проверка буфера и сходимость LNS |
| `python3 -m vrptw.validate buffer` | 3 мин | буфер против расписания смен на новых днях |
| `python3 -m vrptw.slabench` | 6 мин | чем платим за защиту обязательств по SLA |
| `python3 -m vrptw.slabench heldout` | 4 мин | то же на днях, которых при подборе не было |
| `python3 -m vrptw.validate converge` | 3 мин | зависит ли результат от бюджета поиска |
| `python3 -m vrptw.shifts` | 5 мин | вклад расписания смен |
| `python3 -m vrptw.tune` | 5 мин | подбор буфера |

Выгрузка данных для интерфейса:

```bash
python3 -m vrptw.export 1 fixtures          # день 1 в папку fixtures/
python3 -m vrptw.validate_fixtures fixtures # проверка контракта
```

Живой бэкенд вместо статичных файлов — тот же контракт, но с пересчётом
внутри дня по запросу:

```bash
python3 -m vrptw.server        # http://localhost:8000, описание на /api
python3 -m vrptw.server check  # постучаться во все пути и сверить контракт
```

Сверх четырёх форм сервер умеет пересчитывать день по запросу — в том
числе на ЧП с инженером:

```bash
curl 'localhost:8000/api/replan?day=восток&at=720&urgent=2'        # две аварии в 12:00
curl 'localhost:8000/api/replan?day=восток&at=720&disabled=auto'   # сегодня его не будет
curl 'localhost:8000/api/replan?day=восток&at=720&delayed=auto:40' # задержится на 40 минут
curl 'localhost:8000/api/replan?day=восток&at=720&cancelled=auto'  # абонент отказался

# `auto` — движок сам возьмёт того, у кого больше всего работы впереди,
# и заявку, отказ от которой освободит больше всего времени. Номера
# инженеров и заявок у синтетики и у заказчика разные, и команда с
# зашитым номером на зоне отвечает пустым инцидентом либо ошибкой.
```

Выбытие и задержка — намеренно разные запросы: замер говорит, что жать
пересчёт стоит в первом случае и почти незачем во втором.

Семь настроек, которые видит пользователь, отдаются и меняются по
`/api/settings` — и это всё, что движок выпускает наружу. Бюджет поиска,
размер выбивания, шум пересборки и внутренние пороги подобраны замерами,
и любая их правка обесценила бы все измеренные числа.

Сверх этого движку можно сообщить, что произошло на самом деле, и
пересчитать от реальности, а не от разыгранной траектории:

```bash
curl -X POST localhost:8000/api/event -d '{"day":1,"kind":"done","order":"R0012","at":754}'
curl 'localhost:8000/api/state?day=1&at=820'                    # что движок знает
curl 'localhost:8000/api/replan?day=1&at=820&source=journal'    # пересчёт от фактов
```

Без `source=journal` состояние по-прежнему разыгрывается — так меряют и
так показывают демо без диспетчера. Переключение явное нарочно: иначе
качество планировщика однажды измерили бы на выдуманных событиях.
Подробности — в `frontend_kit/SERVER.md`.

Каждый замер печатает доверительные интервалы по парному сравнению.
Число без интервала ничего не значит: разброс между днями больше, чем
разница между планировщиками.

**Числа не зависят от вашей машины.** Бюджет поиска в замерах задан не
секундами, а числом шагов LNS: секунда у каждого своя, шагов у всех
поровну. Секунды печатаются рядом — это latency-обещание, а не единица
измерения качества. Продукт при этом живёт по секундам: в диспетчерской
важна задержка ответа, и сервер считает именно так.

Убедиться, что бюджет вообще ни на что не влияет, проще всего по таблице
сходимости: `python3 -m vrptw.validate converge` показывает, что после
двухсот шагов покрытие уже не меняется, а восемь секунд боевого солвера —
это полторы тысячи шагов.

## Что стоит проверить руками

**Числа не подогнаны под удачные дни.** `bench` принимает число дней:
`python3 -m vrptw.bench 30` берёт втрое больший набор. Проверено:
**+8,3 ± 0,9 п.п. вместо +6,9 ± 1,0 на двенадцати** — интервал сузился,
а не поехал. Точка оценки выше потому, что дни 13–30 для жадного
планировщика труднее; на них же считается held-out.

**Внутренние пороги не подогнаны и не важны.** `COMFORT_SLACK` — запас,
ниже которого солвер штрафует визит за тесноту, — стоит на 40, а жёлтая
подсветка на экране на 45, и это разные числа про разное. Сдвиг
внутреннего порога на 30, 45 или 60 покрытия не меняет ни при утренних
сменах, ни при веере: все интервалы включают ноль.

**Параметры не подогнаны под замер.** Буфер подбирался на днях 1–6,
`validate` меряет на днях 13–30 — тех, которых при настройке не было.

**Буфер зависит от расписания смен, и это меняет постановку.** Подбор
буфера на одном расписании уводит в минус на другом, поэтому
`validate buffer` меряет его сразу на двух, парно, на днях 13–30:

| расписание | буфер 0 | 16 | 30 | 45 |
|---|---|---|---|---|
| как есть | −0,17 ± 0,31 | рабочий | **+0,40 ± 0,27** | +0,22 ± 0,67 |
| веер | **+0,99 ± 0,55** | рабочий | −0,08 ± 0,71 | **−3,81 ± 0,88** |

Буфер полезен ровно настолько, насколько остра нехватка рук. При
утренних сменах работы вдвое больше ёмкости — лишний визит всё равно
почти наверняка сорвётся, и выгоднее защищать уже поставленные. При
веере рук хватает, маршруты длиннее, и требование «запас 45·√позиция» на
девятой позиции вычёркивает визиты, которые прошли бы. Потолок над
буфером компромисс не снимает, а только двигает по той же кривой —
проверено отдельно.

**Переподбор на данных заказчика: значение остаётся 16.** По одному
покрытию шестнадцать выглядит побитой: на веере ноль обыгрывает её
значимо (+0,99 ± 0,55), на утренних сменах тридцать (+0,40 ± 0,27). Но
покрытие — не то, по чему судит ТЗ, и стоило посмотреть на две
обязательные метрики, как картина перевернулась.

| буфер | покрытие | срывов по окну | инженеров | километры |
|---|---|---|---|---|
| 0 | нейтрально | **больше** | нейтрально | хуже на подобранном |
| **16** | — | — | — | — |
| 30 | лучше на подобранном | меньше | **значимо хуже** | хуже на подобранном |
| 45 | **значимо хуже** | меньше | **значимо хуже** | хуже |

На настоящих данных тридцать берёт на 0,33–0,39 инженера больше, и
интервал ноль не включает ни на одном из двух расписаний. Это первая
обязательная метрика ТЗ, и покупать за неё полпункта покрытия — плохая
сделка. Сорок пять хуже сразу по всему. Ноль не покупает ничего:
покрытие нейтрально, срывов по окну больше в полтора раза.

**Шестнадцать не побеждает — она не проигрывает.** Ни одна альтернатива
не обходит её на метриках ТЗ значимо ни в одном из четырёх сочетаний
«данные × расписание». Это и есть ответ на вопрос «почему 16», и он
сильнее прежнего: раньше значение держалось на том, что оно единственное
безопасно в двух режимах по покрытию.

Отдельно стоит заметить, почему этого нельзя было увидеть на синтетике:
там день перегружен, заняты все двенадцать инженеров при любом буфере, и
разница по числу людей ровно ноль во всех строках. Первая метрика ТЗ на
синтетических данных не различает ничего. Мерит `validate zones`. И поэтому же
`buffer_step` вынесен в настройки компании — развёртывание, которое
остаётся на утренних сменах, может поднять его само.

**План не жульничает.** `Plan.check_invariants` проверяется в каждом
замере: заявка не назначается дважды, старт не выходит за окно, финиш не
выходит ни за смену, ни за жёсткую границу дня, инженер не раздваивается.
Главное там — последнее: **время в пути пересчитывается по дорожной сети
на тот час, в который инженер выезжает, и сверяется с тем, что записано в
плане**. Без этого плану ничто не мешает объявить дорогу короче, чем она
есть, и получить красивое покрытие из воздуха. Уберите проверку — увидите,
что она не декоративная: на ней уже поймался ручной профиль смен, сажавший
последнего инженера на смену до 22:00.

**Планировщик не подглядывает в будущее.** Полей с фактическим исходом в
заявке нет вовсе: `selfcheck` это проверяет отдельно. Симулятор
разыгрывает неявку и длительность сам, в каждом прогоне.

**Симуляция даёт живой разброс.** `sd` должен быть около 2 при 55 визитах.
Если он меньше единицы — случайность где-то зафиксирована, и все выводы
о хрупкости плана недействительны.

**Поиск не вырождается.** Ruin & recreate имеет смысл, только если
пересборка может дать не то же самое, что в прошлый раз. Заявке с
единственным возможным местом раньше присваивалось бесконечное
сожаление — а бесконечность нельзя пошевелить шумом, и на маленьких
днях все итерации возвращали одно решение. Теперь сожаление конечно, а
пересборка рандомизирована (`Params.noise`). Проверить просто: поставьте
`noise=0` и запустите `optimumbench` — на дне 20/3 план станет хуже
оптимума на заявку.

**Быстрая версия солвера равна медленной.** `improved.py` и `fast.py` —
один алгоритм, второй переписан на инкрементальных пересчётах. При
нулевом бюджете LNS они обязаны давать один и тот же план визит в визит;
`selfcheck` проверяет это на каждом запуске — и не на голых параметрах,
а на семи наборах, каждый из которых отличается от «без штрафов» ровно
одним слагаемым — неравномерность, вес обязательства, смена исполнителя,
срочность аварий, — плюс боевые значения `Params()` и все слагаемые
разом. Продакшен считает именно с ними, поэтому сверять только нули
бессмысленно. Заодно проверяется,
что каждый штраф вообще меняет план: сверка на параметре, который ни на
что не влияет, ничего и не доказывает. Иначе замеры мерили бы один
солвер, а объяснения относились бы к другому.

## Состав

| Модуль | Что делает |
|---|---|
| `core/osm.py` | настоящая Москва: 600 адресов домов из OSM, матрица времени от OSRM, почасовой профиль пробок, ломаные маршрутов для карты |
| `core/network.py` | какая сеть под стендом — настоящая или синтетическая; выбор один на всех |
| `core/geo.py` | запасная радиально-кольцевая модель, 289 узлов: ей не нужны ни файлы данных, ни интернет |
| `core/domain.py` | модель заявок, инженеров, маршрутов; `Plan.check_invariants` ловит невалидный план |
| `core/generate.py` | синтетический день: 50 районов, окна выдачи, SLA |
| `core/validate_day.py` | годен ли день к планированию и во что он упирается |
| `core/simulate.py` | исполнение дня с каскадом: затянувшийся визит сдвигает последующие |
| `solvers/greedy.py` | базовый жадный планировщик — точка отсчёта |
| `solvers/improved.py` | regret-вставка в любую позицию + буфер до окна + LNS |
| `solvers/fast.py` | то же на инкрементальных пересчётах: 151 итерация/с против 9 |
| `shiftopt.py` | подбор расписания смен: прокси спроса + доводка солвером |
| `replan.py` | пересчёт внутри дня: обрезка дня по текущему моменту, выбытие инженера |
| `dropoutbench.py` | что делать, когда инженер выбыл посреди дня |
| `optimum.py` | точный оптимум как MILP (HiGHS) и доказанная верхняя граница |
| `balancebench.py` | равномерность загрузки: чем за неё платят и кто её портит |
| `stress.py` | другие размеры дня, перекос загрузки, вырожденные случаи |
| `export.py` | выгрузка четырёх форм для интерфейса, см. `CONTRACT.md` |
| `journal.py` | память дня: что сообщил диспетчер, и состояние дня из этого |
| `server.py` | HTTP-сервер: те же формы живьём, пересчёт по запросу, журнал событий |
| `validate_fixtures.py` | проверка того, что контракт обещает интерфейсу |

## Результат

Покрытие дня — доля выполненных из 80 заявок. 12 дней, парное сравнение.

## Обязательства перед абонентом

Покрытие — наша метрика. Заказчик считает другое: сколько обещаний
нарушено. **Половина дня — 39 из 80 заявок — это обязательства на
сегодня**: срок по SLA истекает раньше, чем кончится рабочий день, и
перенести их нельзя. Остальные можно, и «не поехали сегодня» для них не
срыв, а перенос.

Планировщик их не различал: максимизировал число визитов, и заявка с
истекающим сроком стоила ровно столько же, сколько та, что подождёт.
Теперь различает — `Params.sla_weight`, во сколько раз срыв дороже
переноса.

| | срывов в день | покрытие |
|---|---|---|
| без веса | 11,0 | 67,6% |
| **вес 2** | **8,8** | 67,6% |
| вес 3 | 8,7 | 67,4% |
| вес 5 | 8,9 | 67,3% |

**−2,2 ± 0,8 срыва в день, покрытие не меняется** (−0,02 ± 0,43 —
интервал включает ноль). На held-out днях 13–30 то же самое:
**−2,2 ± 0,5 срыва, покрытие −0,04 ± 0,31**.

Дальше двойки срывов почти не убавляется, а покрытие начинает проседать,
поэтому взято два.

Одна оговорка, без которой это звучало бы слишком гладко. Бесплатно
получается не при любом расписании: на веерных сменах защита
обязательств стоит около 0,7 пункта покрытия. В визитах это **0,6 визита
за 2,4 несорванных обязательства** — размен, который бизнес читает сразу,
но это именно размен, а не подарок. Мерит `slabench`, на обоих
расписаниях.

Разрыв до оптимума **0,73%**. На пяти размерах от 20 до 60 заявок HiGHS
доказал оптимум в 12 случаях из 15, и в 11 из этих 12 наш план ему равен.
Ещё в трёх случаях наш план лучше того, что HiGHS нашёл за полторы
минуты. На полном дне из 80 заявок оптимум не доказывается, но разрыв до
доказанной верхней границы — 4,9%: наши 58 визитов против границы 61.

Наш бюджет здесь в шагах, а не в секундах: по секундам число доказанных
совпадений гуляло между прогонами. Сторона решателя остаётся в секундах —
ему дают полторы минуты на день сетки и четыре на полный, — поэтому сама
граница от прогона к прогону может дрогнуть на единицу. Это его
недетерминизм, не наш, и на вывод он не влияет: разрыв считается до
доказанной границы, то есть оценка всегда сверху.

Чтобы эти числа появились, точную модель пришлось переписать. В наивном
виде она на полном дне не давала ничего: находила единицы визитов и не
двигала границу. Три вещи, ни одна из которых не меняет оптимум:

- **мёртвые дуги не создаются.** Переменная заводится, только если у
  инженера есть навык в обоих концах и по дуге вообще можно успеть в
  окно. Это выбрасывает три четверти из восьмидесяти тысяч переменных;
- **большая константа своя у каждой дуги** вместо одной на всех в двое
  суток. Обычно это три-десять часов — ровно на этот множитель и была
  разболтана линейная релаксация, по которой решатель судит о своём
  расстоянии до оптимума;
- **ёмкость времени записана явно.** Её не было вовсе, и диагностика
  показала, где настоящее узкое место дня: в окно 17–21 приходит 24 часа
  работы, а смен в это время открыто 7 часов. Теперь для каждого
  интервала суток считается, сколько минут работы он обязан вместить и
  сколько человеко-минут смен в нём открыто.

Отсечения валидны — проверено сверкой со старой моделью: везде, где та
доказывала оптимум, новая даёт то же число. А доказывает она заметно
больше: на 45 заявках день, который старая модель не осилила за полторы
минуты, новая закрывает за шесть секунд.

**И тут же нашлось, чего мы не умеем.** В одном из одиннадцати доказанных
случаев наш план на визит хуже оптимума: 29 против 30. Проверил, в чём
дело — не в бюджете: 1500 шагов поиска и 40 000 дают одни и те же 29.
А другое зерно даёт 30. То есть поиск застревает, и лечится это
перезапусками, а не временем.

Гипотезу проверил: реализовал перезапуски в обеих версиях солвера и
померил. **Не работает** — тот случай остался на 29 при 2, 3, 4 и 6
заходах, а на основной конфигурации деление бюджета только отнимает
(−0,03…−0,22 п.п.). Откатил. Но это и есть настоящая работа точного
оптимума: он не украшает презентацию, он показывает, где именно
планировщик недотягивает, и позволяет проверить догадку, а не поверить
в неё.

Пересчёт внутри дня: две аварии в 13:40 с трёхчасовым окном. Без пересчёта
они уезжают на завтра, с пересчётом выполняется 1,8 из 2, и всего за день
на 2,9 визита больше. Новый план готов за 1,5 секунды и сохраняет 90%
назначений — инженеры, которым уже сказали ехать, продолжают ехать.
Промедление стоит дёшево: пересчёт через час вместо немедленного
теряет 0,8 визита. Ценность здесь в самом
факте пересчёта, а не в секундах реакции — и это ровно то, что делает
демо честным: мы не продаём полторы секунды как решающие.

Выбытие инженера посреди дня. Случайный инженер с незакрытой работой
исчезает до конца дня; сравнение с тем же днём, где он на месте, и с той
же бригадой, которая едет по прежнему плану.

| Момент | Визитов у него | Как ехали | Пересчёт | Разница |
|---|---|---|---|---|
| 10:00 | 4,2 | 49,8 | 53,0 | **+3,2 ± 0,7** |
| 13:00 | 3,2 | 49,5 | 52,7 | **+3,1 ± 1,0** |
| 16:00 | 1,5 | 51,1 | 51,1 | +0,0 ± 0,2 |

Само выбытие стоит дню 3,8 визита при утреннем сроке; пересчёт возвращает
2,9 из них и оставляет 92% чужих визитов у прежних исполнителей. К вечеру
компенсировать уже нечего: в 16:00 потеря −1,2 визита остаётся −1,1 и с
пересчётом. Прирост в этот час (+0,0) даёт не спасение выбывшего, а
обычная переоптимизация остатка — эти два эффекта в замере разделены.

А вот прокол колеса на 40 минут оказался не событием вовсе: **он стоит дню
0,3 визита**, потому что буферы в маршруте его и так съедают. Из этой
потери пересчёт возвращает 0,1–0,3 визита. Кнопка при этом покажет
+0,0…+1,5 — но это не спасение от прокола, а обычная
переоптимизация остатка, которую можно было сделать и без всякого ЧП;
в замере эти два эффекта разделены нарочно. Различать «инженер
задержался» и «инженера сегодня не будет» важнее, чем пересчитывать в
обоих случаях: система, перетасовывающая бригаду из-за сорокаминутной
задержки, хуже той, что не делает ничего.

Равномерность загрузки выравнивается бесплатно. Джини по занятости
падает с 0,081 до 0,051, разрыв между самым и наименее занятым — с 49 до
26 пунктов, инженеров без единого визита не остаётся вовсе; покрытие при
этом не меняется (−0,3 ± 0,8 п.п. — интервал включает ноль). На утренних
сменах эффект впятеро сильнее: Джини 0,238 → 0,081, и там штраф убирает
двух простаивающих инженеров в день.

Но главную часть неравномерности лечит не алгоритм. При утренних сменах
без единого визита остаётся два установщика — весь неразмещённый
спрос в такие дни открывается после 17:00, и человеку со сменой до 17:00
взять его нечем. Расписание само по себе снижает Джини с 0,238 до 0,082,
штраф добивает до 0,051.

Подбор смен идёт в два этапа. Прокси размазывает спрос по окнам заявок и
считает непокрытие — оценка за доли миллисекунды, корреляция с настоящим
покрытием −0,93. Затем доводка: локальный подъём с оценкой настоящим
солвером, потому что прокси не знает географии и недобирает около трёх
пунктов (+4,6, причём выигрыш переносится на независимые прогоны
симуляции — то есть он настоящий, а не подгонка под конкретные случайные
числа).

Сам по себе прокси ручной веер не обыгрывает (+0,9 ± 1,7 — интервал
включает ноль), и это честнее, чем звучало бы «автоподбор лучше руками».
Обыгрывает связка: доводка добавляет +2,4 ± 1,1 сверх прокси, выводит на
+3,4 ± 1,4 против ручного веера и на +14,1 ± 2,3 против исходного
расписания.

Доводка идёт по той же лексикографической цели, что и солвер: сперва
покрытие, затем число задействованных исполнителей, затем пробег. Раньше
она смотрела только на покрытие и останавливалась, как только очередной
сдвиг переставал его двигать. Теперь ход, оставляющий покрытие в пределах
шума, но освобождающий человека или срезающий километры, тоже принимается
— и подъём проходит плато вместо того, чтобы вставать на нём. Отсюда
+2,4 против прежних +1,7 над прокси.

На данных заказчика эта правка ничего не дала: покрытие +0,33 ± 0,40,
инженеров −0,04 ± 0,08, пробег −8,7 ± 12,1 — все три интервала включают
ноль. День там наполовину пустой, сдвиг часа выхода почти не меняет, кто
именно задействован, и второму уровню цели не за что зацепиться.

## Где стена по размеру дня

`stress` проверяет размеры до 240 заявок на нашем пуле адресов. Но
настоящих заявок у городской выездной службы может быть и шестьсот, а
масштаб мы узнаем только 15 сентября. `scalebench` строит сеть под
координаты самого дня и смотрит, где кончается бюджет поиска.

| Заявок / инженеров | Жадный | Наш | Разница | Первая сборка | Шагов за 8 с | Шагов/с |
|---|---|---|---|---|---|---|
| 80 / 12 | 71,0% | 77,3% | +6,2 | 0,0 с | 1596 | 199 |
| 240 / 36 | 71,3% | 78,1% | +6,8 | 0,6 с | 397 | 49 |
| 400 / 60 | 73,5% | 82,7% | +9,2 | 2,3 с | 260 | 32 |
| **600 / 90** | 73,2% | 79,2% | +6,0 | **6,7 с** | **98** | 12 |

**Преимущество над жадным держится везде** — от +6,0 до +9,2. Значит
выводы не были свойством конкретного размера.

А вот бюджета перестаёт хватать. Результат выходит на плато после
двухсот шагов поиска; на шестистах заявках за восемь секунд успевает
девяносто восемь. Причин две, и вторая важнее: **первая сборка плана
съедает 6,7 секунды из восьми.** Regret-вставка квадратична по числу
заявок, и на большом дне улучшать уже нечем — бюджет кончился на
построении.

Оговорка, которая делает картину хуже, а не лучше: плато в двести шагов
измерено на восьмидесяти заявках. На шестистах его, скорее всего, надо
искать выше — большому дню нужно больше шагов, а не меньше.

**Что с этим делать, если реальный день окажется большим.** План на
завтра считается один раз с вечера, и там восемь секунд можно смело
менять на минуту — это ничего не стоит. Настоящая проблема в другом:
**обещание «пересчёт за полторы секунды» ломается раньше.** Пересчёт
работает с остатком дня, но если в остатке триста заявок, одна только
сборка займёт больше секунды, и улучшать будет нечем. Тогда либо
поднимать бюджет пересчёта, либо пересобирать не весь остаток, а только
задетую часть — маршрут выбывшего плюс соседей. Второе мы не делали и не
мерили.

При перекосе по загрузке (те же 80 заявок, бригада от 6 до 24 человек)
выигрыш тоже держится: от +4,6 до +7,0 пункта. Заметно другое: чем
свободнее бригада, тем неравномернее загрузка — при 24 инженерах Джини
0,26 против 0,04 при шести, просто потому, что работы на всех не
хватает.


Подробный журнал переезда — `ПЕРЕЕЗД-15-09.md` в корне. Здесь три вещи,
без которых числа выше читаются неправильно.

**ТЗ судит по другим метрикам.** Дословно: «выполнение всех заявок
наименьшим количеством персонала» и «пробег по маршруту каждого
исполнителя». Покрытия дня, главной метрики этого README, в ТЗ нет
вообще. Обе теперь считаются — `Plan.metrics(day)` — и едут в выгрузку.

**День заказчика выполнимый, а не перегруженный.** Отношение работы к
ёмкости смен 0,41–0,61: рук примерно вдвое больше, чем работы. Весь
разбор выше построен на обратном случае, и на таких данных покрытие
планы почти не различает — различают число людей и километры.

**Базовый вариант ТЗ — не наш `greedy`.** ТЗ задаёт его дословно: заявки
по порядку поступления, первому по порядку доступному инженеру, порядок
посещения равен порядку назначения. Написан отдельно,
`solvers/sequential.py`, и сравниваться надо с ним:

| зона | базовый ТЗ | наш | км на визит |
|---|---|---|---|
| Восток | 24/66 | 61,0/66 | 5,10 → 4,53 |
| Юго-восток | 36/83 | 72,2/83 | 18,36 → 11,98 |
| Югоцентр | 18/56 | 55,0/56 | 5,42 → 3,95 |
| **итого** | **78/205 (38%)** | **188/205 (92%)** | **9,63 → 6,82 (−29%)** |

Пробег валом сравнивать нельзя: наш план проезжает больше километров
просто потому, что выполняет втрое больше заявок. Честно — километры на
выполненный визит.

Доверительного интервала по дням здесь нет и быть не может: день один,
зоны три. Разброс по сидам внутри зоны есть, разброса по дням нет, и
выдавать одно за другое мы не будем.

### Сеть под произвольные адреса

Координат в выгрузке не было — только почтовые адреса. Прямой геокодер
`core/geocode.py` разбирает их и ходит в Nominatim, а при отказе — в
Photon; результат в постоянном кэше `data/geocode.json`, так что
**на защите интернет не нужен**. Из 198 адресов 190 найдены домом, 8
улицей, ни один не потерян.

Сеть строится под тот набор точек, который прислали:

```bash
python3 -m vrptw.core.osm points адреса.json
```

Нужны только `lat` и `lon`. Совпадающие координаты схлопываются в один
узел: несколько заявок в одном доме дело обычное. Матрица считается один
раз и кладётся в кэш под отпечатком набора. Из кода это
`network_for_points(точки)`.

**Во что это обходится.** Матрица растёт как квадрат числа узлов, а
публичный OSRM отдаёт не больше сотни координат за запрос: на 600 точках
это 144 запроса и минут десять, на 2000 — уже полторы тысячи. Начиная
примерно с тысячи точек нужен свой OSRM:

```bash
docker run -p 5000:5000 osrm/osrm-backend osrm-routed /data/moscow.osrm
VRPTW_OSRM=http://localhost:5000 python3 -m vrptw.core.osm points адреса.json
```

### Что осталось априорным

`no_show_rate` и `spread` в `WorkType` оценить не по чему: фактической
длительности визита и отметки о неявке в выгрузке нет. Они остались
нашими прежними, и это записано в допущениях загрузчика. Как только
появится история выполнения — пересчитать по шагу 5 `MIGRATION.md`.

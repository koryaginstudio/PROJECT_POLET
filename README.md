# Планировщик выездов инженеров

> **Ветка `движок-сборка`** — движок с собранным интерфейсом, всё в одном:
> `pip install -r requirements.txt`, потом
> `python3 -m vrptw.server 8000 восток,юго-восток,югоцентр` и открыть
> http://localhost:8000. Исходники интерфейса — отдельно, в ветках `движок`
> и `движок-правки` этого же репозитория (правки поверх `main`); из какой
> собран `web/`, написано в `web/сборка.json`. Снимок без истории и рабочих
> записок; контрольных выгрузок в нём нет.

Хакатон «Лидеры цифровой трансформации», задача от «Билайн Бизнес»:
интеллектуальный сервис планирования рабочих маршрутов для выездных
инженеров с учётом временных окон и сложности работ.

Сервис распределяет заявки между инженерами и строит порядок объезда,
считает обе обязательные метрики ТЗ и сравнивает их с базовым вариантом,
объясняет, почему заявка у этого инженера и почему другая осталась без
исполнителя, пересчитывает остаток дня на аварию, отказ абонента, выбытие
или задержку инженера, принимает ручное переназначение и статусы от
диспетчера и отвечает, сколько ещё людей нужно, чтобы закрыть то, что не
влезло.

Всё считается на обезличенной выгрузке, выданной организаторами, за
17.08.2026 — три участка, 205 заявок. Контрольную выборку не используем
нигде: её не читает ни один путь исполнения. Интернет не нужен: адреса геокодированы заранее, дорожные
матрицы и ломаные по улицам лежат в репозитории. Свою выгрузку дня того же
формата можно загрузить кнопкой; интернет понадобится, только если в ней
есть адреса, которых нет в выданной выгрузке, — их надо найти
(около 1,4 с на адрес) и достроить под них сеть дорог.

## Запустить

Нужен Python 3.10 или новее. Из корня репозитория:

```bash
pip install -r requirements.txt
python3 -m vrptw.server 8000 восток,юго-восток,югоцентр
```

Открыть **http://localhost:8000** — там интерфейс диспетчера. Он лежит в
`web/` собранным, поэтому ни node, ни сборки не нужно. (Собран из ветки
«движок» репозитория интерфейса командой `zsh собрать-интерфейс.sh`; какой
коммит — в `web/сборка.json`.)

**Сколько ждать.** Порт открывается сразу. Планы трёх участков на этом
коде лежат готовыми в `vrptw/data/готовые/` — с ними день поднимается за
секунды. Если движок правили, готовые планы перестают подходить (в имени
файла — отпечаток кода), и сервер считает сам: на обычном ноутбуке около
трёх минут. Страница в это время пишет, сколько участков готово, и
открывается сама.

Все команды — из корня репозитория: сервер пишет своё состояние (архив
расчётов, журнал диспетчера) в текущий каталог.

## Сценарий ТЗ по шагам

| шаг ТЗ | в интерфейсе | то же через API |
|---|---|---|
| 1. Открыть тестовый набор | «Диспетчерская» → расчёт участка; свой файл — «Создать расчёт» → «Загрузить выгрузку дня» | `/api/plan?day=восток`, `POST /api/uploads` |
| 2. Запустить планирование | «Создать расчёт», переменные движка | `POST /api/runs` |
| 3. Маршруты на карте | вкладка «Обзор» — маршруты по улицам | `routes[].stops[].geometry` |
| 4. Почему этот инженер | точка на карте → «Почему этот исполнитель» | `/api/explain?day=восток` |
| 5. Авария / отмена / выбытие | «Воздействия» → карточка события | `/api/replan?day=восток&at=820&urgent=2` |
| 6. Что изменилось | окно «Что дал пересчёт» | `meta.replan` |

Сверх сценария: метрики ТЗ и сравнение с базовым — плитки «Исполнителей» и
«Пробег» на пульте (`meta.baseline`); почему заявка без исполнителя — в её
карточке (`unassigned_detail`); ручное закрепление и статусы «отправлено /
в пути / выполнено / сорвано» — в карточке заявки (`POST /api/event`);
«сколько ещё людей нужно» — на «Воздействиях» (`/api/staffing`). Все
ручки и поля — в `vrptw/CONTRACT.md` и `frontend_kit/SERVER.md`.

## Как проверить, что всё работает

```bash
python3 -m vrptw.selfcheck        # ~35 с: весь путь движка, 40 отметок
python3 -m vrptw.server check     # до 8 мин на холодном кэше: все ручки, 78 отметок
zsh проверка-с-нуля.sh            # клон репозитория с нуля — то, что увидите вы
```

`selfcheck` и `server check` — это и есть набор тестов. Каждый план,
который выходит наружу, проверяется `Plan.check_invariants`: окна, смены,
навык, транспорт и предел перегона, время в пути по дорожной сети на час
выезда, длительность работ и граница суток (22:00). Соврать ему нельзя —
он пересчитывает всё сам.

## Что оптимизируется

Критерии — в порядке, названном заказчиком:

1. **больше выполненных заявок**; внутри — приоритет распределения:
   авария → подключение → ремонт и дозаказ (нераспределённая авария хуже
   любого числа нераспределённых подключений);
2. **меньше исполнителей**;
3. **меньше пробег**.

Алгоритм — regret-вставка и поиск большими окрестностями (разрушить и
пересобрать, с отжигом), `vrptw/solvers/`. Две реализации одного
алгоритма — `fast.py` (боевой) и `improved.py` (эталон) — сверяются в
`selfcheck` шаг в шаг. Пошагово — `ФУНКЦИОНАЛЬНЫЕ-ТРЕБОВАНИЯ.md`, раздел 3.

## Числа

Каждое число — с файлом замера и парным 95% интервалом по всем источникам
случайности, если он есть. Файлы — в `замеры-21-09/`.

**Против базового варианта ТЗ**, три участка вместе
(`база-против-нас.txt`, `база-против-нас-интервалы.txt`, 8 зёрен):

| | базовый | наш | разница |
|---|---|---|---|
| назначено из 205 | 81,0 | 192,2 | +111,2 ± 0,4 |
| выполнено (симуляция дня) | 70,5 | 169,7 | +99,1 ± 0,5 |
| исполнителей | 42,0 | 38,8 | −3,2 ± 0,4 |
| км на назначенный визит | 12,51 | 6,15 | −50,8% ± 2,7% |

Пробег валом сравнивать нельзя: мы назначаем в 2,4 раза больше заявок.
На участке «Восток» после правки двух адресов мы тоже выигрываем:
−0,40 ± 0,10 км на визит (до неё проигрывали +0,31 ± 0,13).

**Насколько близко к пределу** (`потолок-час.txt`): точная модель на HiGHS
за час. Югоцентр 56 из 56 — оптимум доказан. Восток: наш план в том же режиме
берёт 64 при верхней границе 64,0, HiGHS за час нашёл 63. Юго-восток:
наш 76, HiGHS за час 66, доказанная граница 81 — от нас до предела не
больше пяти заявок.

**Пересчёт в течение дня** (`замеры-22-09/пересчёт-на-зонах.txt`,
`выбытие-на-зонах.txt`, `прокол-на-зонах.txt`): две аварии — +1,7 ± 0,8
визита за 1,5 с, у 86–89% визитов исполнитель не меняется; выбытие
инженера утром стоит 4,4 визита, пересчёт возвращает 2,9 ± 1,1; задержка
на 40 минут стоит 0,1–0,2 визита, и пересчёт из неё не возвращает ничего —
буферы съедают её сами.

**Сколько ещё людей нужно** (`сколько-людей.txt`): Восток +3, Юго-восток
+5, Югоцентр 0.

**Где ломается день** (`окна-спрос.txt`): окно 10:00–12:00 — на
подключения спрос 28,7 ч работы против 21,0 ч рук.

## Данные и допущения

Выгрузка за 17.08.2026 — `vrptw/data/заявки/`: Восток 66 заявок,
Юго-восток 83, Югоцентр 56; внизу каждого файла — адрес офиса участка,
стартовая точка инженеров. Координат, длительности работ, приоритета,
транспорта и самих инженеров в выгрузке нет; ТЗ разрешает их достроить и
требует назвать допущения:

```bash
python3 -m vrptw.core.load допущения
```

Коротко: длительность — по виду работ, приоритет — по типу заявки,
бригада, транспорт и смены — по правилам ТЗ; оборудование на заявку —
наше допущение по виду работ (постановщик разрешил синтетику). Ни одно
допущение не касается того, как визит прошёл на самом деле: неявку и
разброс длительности симулятор разыгрывает заново в каждом прогоне,
планировщик будущего не видит. Подробно — `ФУНКЦИОНАЛЬНЫЕ-ТРЕБОВАНИЯ.md`,
раздел 5.

## Чего система не делает

* Вероятность неявки и разброс длительности — априорные: истории визитов
  в выгрузке нет.
* Интервала по дням на настоящих данных нет: день один, разложенный на
  три участка. Интервалы выше — по зёрнам солвера и симуляции.
* Оборудование между исполнителями при встрече не передаётся: в машине
  то, что выдали утром.

Полный список — `ФУНКЦИОНАЛЬНЫЕ-ТРЕБОВАНИЯ.md`, раздел 6.

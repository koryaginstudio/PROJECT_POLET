# Контракт данных для интерфейса

Версия схемы **1.0**. Четыре формы, каждая под свой экран:

| Файл | Экран | Размер |
|---|---|---|
| `plan.json` | карта и таймлайн смены | ~64 КБ |
| `explain.json` | панель «почему так» | ~150 КБ |
| `simulation.json` | сводка дня | ~1 КБ |
| `shifts.json` | график выхода | ~6 КБ |

Примеры лежат в `fixtures/`. Пересобрать: `python3 -m vrptw.export <seed> <папка>`.
Разные `seed` дают разные дни — удобно проверять вёрстку на нескольких наборах.

Те же формы отдаются живьём: `python3 -m vrptw.server` поднимает
`http://localhost:8000`, где `fetch('day-01/plan.json')` превращается в
`fetch('/api/plan?day=1')`. Формат ответа не меняется, поэтому переключение
с фикстур на сервер ничего в вёрстке не ломает. Сверх контракта сервер умеет
пересчитывать день по запросу — `GET /api/replan?day=1&at=820&urgent=2`
возвращает такой же `plan`, но на остаток дня и с блоком `meta.replan`
(время решения, стабильность, сколько аварий влезло, сколько было бы без
пересчёта). Подробности — в `SERVER.md`.

## Общее для всех форм

**Время — целое число минут от полуночи.** `540` = 09:00, `1080` = 18:00.
Так позиции на таймлайне считаются арифметикой без разбора дат.
Форматирование — на стороне интерфейса:

```js
const hhmm = m => `${String(Math.floor(m / 60)).padStart(2, '0')}:${String(m % 60).padStart(2, '0')}`
```

День укладывается в диапазон примерно `420…1260` (07:00–21:00). После 21:00
инженер не работает ни при каких условиях — это жёсткая граница.

**Координаты** — `lat` / `lon`, градусы, шесть знаков.

**Идентификаторы** — строки: заявки `R0000`, инженеры `E00`. Стабильны внутри
одного дня; между днями не переносятся.

Каждый файл начинается с `schema` и `kind` — по ним можно проверить, что
загружено то, что ожидалось.

## plan.json

```jsonc
{
  "schema": "1.0",
  "kind": "plan",
  "meta": {
    "date": "2026-09-15",
    "generated_at": 1788455755,          // unix-время сборки
    "time_format": "minutes_from_midnight",
    "solver": "fast/regret+lns",
    "orders_total": 80,
    "orders_assigned": 55,
    "engineers_total": 12,
    "balance": {                         // равномерность загрузки
      "gini": 0.081,                     // 0 — все заняты одинаково, 1 — весь день везёт один
      "occupancy_min": 0.383,
      "occupancy_max": 0.722,
      "occupancy_mean": 0.556,
      "idle_engineers": 0                // сколько инженеров без единого визита
    }
  },
  "engineers": [ ... ],
  "orders":    [ ... ],
  "routes":    [ ... ],
  "unassigned": ["R0003", "R0011"]       // id заявок, не попавших в план
}
```

### engineers[]

| Поле | Тип | Значение |
|---|---|---|
| `id` | string | `E00` |
| `name` | string | фамилия |
| `skills` | string[] | `install` / `repair` / `line` |
| `grade` | int | 1–3, выше — опытнее |
| `shift_start`, `shift_end` | int | границы смены, минуты |
| `home_lat`, `home_lon` | float | откуда выезжает и куда возвращается |

### orders[]

| Поле | Тип | Значение |
|---|---|---|
| `id` | string | `R0000` |
| `work_type` | string | `install`, `repair`, `diag`, `cpe`, `line` |
| `work_title` | string | название по-русски: «Подключение» |
| `skill` | string | какой навык нужен |
| `district` | string | район Москвы |
| `lat`, `lon` | float | адрес |
| `window_start`, `window_end` | int | окно, обещанное абоненту |
| `sla_deadline` | int | крайний срок; может быть больше `window_end` — тогда заявку можно перенести на завтра |
| `priority` | int | 0 обычная, 1 повторный визит, 2 авария |
| `est_minutes` | int | оценка длительности работ |
| `needs_access` | bool | нужен доступ в подъезд или квартиру |
| `assigned_to` | string \| null | id инженера или `null` |

### routes[]

Один элемент на инженера, у которого есть визиты. Инженер без визитов в
`routes` не появляется — но остаётся в `engineers`.

```jsonc
{
  "engineer_id": "E00",
  "stops": [
    {
      "seq": 0,                    // порядок в маршруте
      "order_id": "R0019",
      "arrive": 559,               // когда подъехал
      "start": 559,                // когда приступил (не раньше окна)
      "finish": 589,               // когда закончил
      "travel_minutes": 19,        // дорога до этой точки
      "wait_minutes": 0,           // ждал открытия окна
      "slack_minutes": 101,        // запас: на сколько можно опоздать
      "risk": "low",               // low | medium | high — по slack
      "geometry": [[55.75,37.61], ...]   // линия для карты
    }
  ],
  "totals": {
    "visits": 6, "travel_minutes": 111, "work_minutes": 340,
    "idle_minutes": 76, "start": 540, "end": 1067, "overtime_minutes": 0,
    "occupancy": 0.556           // доля смены на работу и дорогу
  }
}
```

**`occupancy`** — `(work_minutes + travel_minutes) / (shift_end − shift_start)`.
Ожидание открытия окна в занятость не входит: инженер, который час ждёт окна,
занят не по своей вине, и записывать это ему в нагрузку нечестно. Готовая
шкала загрузки: у нас она держится в пределах 34–83%, а `meta.balance.gini`
даёт одну цифру равномерности на весь день.

**`geometry`** — ломаная от предыдущей точки маршрута до адреса заявки, по
узлам дорожной сети. Первый перегон начинается от дома инженера. Кладётся
прямо в полилинию карты. Сейчас это узлы нашей радиально-кольцевой модели
Москвы; с настоящими данными сюда придёт полилиния настоящего маршрутизатора,
формат поля не изменится.

**`risk`** — производное от `slack_minutes`: `high` при запасе меньше 20 минут,
`medium` до 45, дальше `low`. Это детерминированная оценка «насколько впритык
стоит визит». Вероятность срыва с учётом всех случайностей — в
`simulation.json → fragile`, и это разные вещи: визит может стоять с большим
запасом, но сорваться из-за неявки абонента.

### Что гарантируется

Проверяется при сборке, можно на это опираться:

- каждый `order.id` встречается в `orders` ровно один раз;
- `assigned_to` либо `null`, либо существующий `engineers[].id`;
- `unassigned` — ровно те заявки, у которых `assigned_to === null`;
- `stops` отсортированы по `seq`, и `start` внутри маршрута строго растёт;
- `arrive ≤ start ≤ finish` для каждой остановки;
- `window_start ≤ start ≤ window_end` — план никогда не ставит визит вне окна;
- `finish ≤ shift_end` — план не выходит за смену (переработка возможна только
  в исполнении, не в плане);
- `stops[i].arrive ≥ stops[i-1].finish` — инженер не раздваивается;
- `totals.occupancy` сходится с `work_minutes`, `travel_minutes` и длиной смены;
- `meta.balance.gini` лежит в `[0, 1]`.

## explain.json

Для панели «почему эта заявка у этого инженера». Ключ — id заявки, есть запись
для каждой заявки дня, включая нераспределённые.

```jsonc
{
  "schema": "1.0", "kind": "explain",
  "meta": { "date": "...", "cost_units": "минуты пути плюс штрафы за простой и риск" },
  "orders": {
    "R0000": {
      "assigned_to": "E09",
      "summary": "назначен Семёнов: дешевле всех остальных из 5 подходящих",
      "candidates": [
        { "engineer_id": "E03", "verdict": "chosen",   "cost": -17.2, "note": "назначен" },
        { "engineer_id": "E01", "verdict": "feasible", "cost": 151.8, "note": "мог бы, но обошёлся бы дороже на 169" },
        { "engineer_id": "E00", "verdict": "no_room",  "cost": null,  "note": "маршрут уже занят в это время" },
        { "engineer_id": "E06", "verdict": "no_skill", "cost": null,  "note": "нет навыка «install»" }
      ]
    }
  }
}
```

`candidates` содержит **всех** инженеров дня — так панель может показать полную
картину, а не только победителя.

| `verdict` | Значение |
|---|---|
| `chosen` | назначен ему |
| `feasible` | мог бы взять, но дороже; `cost` заполнен |
| `no_room` | навык есть, смена подходит, но маршрут занят в это время |
| `shift_mismatch` | окно заявки не пересекается с его сменой |
| `no_skill` | нет нужного навыка |

`cost` — во сколько обошлась бы вставка этому инженеру: минуты пути плюс штрафы
за простой и за визит впритык к окну. Сравнивать имеет смысл только между
кандидатами одной заявки.

**`cost` бывает отрицательным** — и это не ошибка. Визит, вставший в дыру между
двумя другими, убирает простой, и сэкономленное ожидание перевешивает
добавленную дорогу. Такие вставки для планировщика самые выгодные. Показывать
пользователю сырое число не стоит; сортируйте по нему и берите готовый `note`.

`summary` — готовая фраза для заголовка панели. Для нераспределённых заявок она
объясняет причину: «в окно этой заявки никто не работает», «все подходящие
инженеры заняты», «никто не владеет нужным навыком».

## simulation.json

Что будет, если этот план исполнить. Триста прогонов со случайными пробками,
разбросом длительностей, неявками абонентов и проблемами с доступом.

```jsonc
{
  "schema": "1.0", "kind": "simulation",
  "meta": { "date": "...", "runs": 300 },
  "planned": 55,            // визитов в плане
  "orders_total": 80,       // заявок в дне
  "done": { "mean": 48.99, "p10": 46, "p50": 49, "p90": 52, "sd": 2.2 },
  "coverage": 61.2,         // % выполненных ОТ ВСЕХ заявок дня — главная метрика
  "execution_rate": 89.1,   // % выполненных от запланированных
  "reasons": { "no_show": 3.56, "missed_window": 1.21, "no_access": 1.13, "dropped": 0.1 },
  "overtime_minutes": 106.2,
  "idle_minutes": 957.4,
  "fragile": [ { "order_id": "R0061", "failure_rate": 29.3 } ]
}
```

**Показывать надо `coverage`.** `execution_rate` выглядит внушительнее, но почти
не зависит от качества плана — его определяют неявки абонентов. Если вынести
крупной цифрой именно его, интерфейс будет хвалить планировщик за то, к чему он
не имеет отношения.

`reasons` — среднее число срывов за день по причинам:

| Причина | Что произошло |
|---|---|
| `no_show` | абонента не было дома |
| `missed_window` | приехали, когда окно уже закрылось — это каскад от предыдущих задержек |
| `no_access` | не попали в подъезд |
| `dropped` | до визита не доехали, смена кончилась |

`fragile` — до десяти заявок с наибольшей долей прогонов, в которых визит
сорвался. Это самый полезный список для диспетчера: он показывает, где план
держится на честном слове.

## shifts.json

График выхода на смену: сколько людей нужно и когда, против того, как есть
сейчас.

```jsonc
{
  "schema": "1.0", "kind": "shifts",
  "meta": {
    "shift_hours": 9,
    "allowed_starts": ["07:00", "08:00", "09:00", "10:00", "11:00", "12:00"],
    "demand_units": "инженеров одновременно, с учётом дороги"
  },
  "current":     { "profile": {"08:00": 6, "09:00": 6}, "expected_coverage": 61.2 },
  "recommended": {
    "profile": {"08:00": 1, "09:00": 1, "10:00": 2, "11:00": 1, "12:00": 7},
    "expected_coverage": 86.4,
    "starts_by_engineer": { "E00": "12:00", "E01": "09:00" }
  },
  "curve": [
    { "minute": 540,
      "demand": { "install": 2.31, "repair": 1.08, "line": 0.2 },
      "demand_total": 3.59,
      "supply_current": 6,
      "supply_recommended": 2 }
  ]
}
```

`curve` — шаг 30 минут, с 06:00 до 22:00; ранние и поздние точки нулевые. Готовые ряды для графика «спрос против
предложения»: две линии предложения и область спроса под ними. Именно здесь
видно главное — спрос смещён в вечер, а смены кончаются днём.

Разница `expected_coverage` между `current` и `recommended` — это то, что даёт
один только перенос смен, без изменений в маршрутизации.

## Как это будет получено в реальной системе

Сейчас файлы собираются скриптом из синтетического дня. Формы задуманы так,
чтобы при переходе на HTTP ничего не менялось: те же четыре тела ответов на
`GET /plan`, `/explain`, `/simulation`, `/shifts` с параметром даты. Поэтому
загрузку стоит спрятать за одну функцию — подменить `fetch('/fixtures/plan.json')`
на `fetch('/api/plan?date=...')` должно быть достаточно.

**Что изменится 15 сентября**, когда откроется ТЗ: состав справочников. Коды
работ, названия навыков, число инженеров, границы смен — всё это придёт из
настоящих данных и почти наверняка не совпадёт с нынешними. Поэтому не стоит
зашивать в вёрстку конкретные значения `work_type` и `skills`: перечисляйте то,
что пришло в файле. Структура форм и типы полей меняться не должны; если
придётся — версия схемы вырастет, и это будет отдельно оговорено.

Заведомо неизвестное на сегодня: будет ли в данных история выполнения (от неё
зависит, сможем ли мы оценивать вероятность неявки по-настоящему, а не
априорно) и в каком виде придёт матрица совместимости инженеров и работ.

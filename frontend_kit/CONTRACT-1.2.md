# Контракт данных, схема 1.2

Дополнение к [`CONTRACT.md`](CONTRACT.md) — не замена. Здесь описано только то,
что схема 1.2 добавляет к 1.1; всё, что не упомянуто, работает по-прежнему и
слово в слово.

## Зачем понадобилась 1.2

15 сентября открылось настоящее ТЗ «Билайн Бизнес» и пришла выгрузка заявок за
17 августа по трём зонам. Сверка показала три вещи.

Первая: из трёх обязательных групп ограничений ТЗ стенд проверяет две. Нет
ограничения по транспорту — ни поля у заявки, ни поля у инженера, ни отказа с
такой причиной.

Вторая: обязательная метрика ТЗ — пробег в километрах по каждому исполнителю и
суммарно. Стенд считает время в пути в минутах. Расстояния в движке есть
(`road_km` в дорожной сети), наружу они не выходят.

Третья: ТЗ требует сравнения с базовым вариантом по двум метрикам. Жадный
солвер в движке написан и замеряется, но контракт не предусматривает способа
показать его план рядом с основным.

Всё остальное в 1.2 — поля, которых требует интерфейс диспетчера и новый
интерфейс инженера: фактический ход визита, ручное закрепление заявки, контакт
на объекте, транспорт и оборудование.

## Правило совместимости

**Поля только добавляются. Ни одно не переименовано и не убрано.** Всё новое
приходит как `null` либо отсутствует, если движок его ещё не отдаёт, — ровно
так же, как в 1.1 приходили пустыми адреса на синтетической сети.

Отсюда правило для вёрстки: **проверять на `null`, а не на отсутствие ключа**, и
показывать «нет данных» вместо пустого места. Интерфейс, собранный под 1.2,
обязан работать на движке 1.1 без единой ошибки — просто часть карточек будет
беднее.

Отсюда же правило для проверки версии: интерфейс сверяет **старшую цифру**
схемы, а не строку целиком. `1.1` и `1.2` принимаются оба, `2.0` — отвергается.
Младшая версия по этому контракту всегда дополняющая, и отвергать данные
из-за неё значит наказывать себя за собственное обещание.

## Общее

**Расстояние — километры, дробное число, два знака.** `4.17` — это 4 км 170 м.
Минуты в пути остаются там, где были: это разные величины, и одна из другой не
считается — тридцать минут по центру и тридцать минут по вылетной магистрали
это разный пробег.

**Коды справочников по-прежнему не зашиваются в вёрстку.** Перечисляем то, что
пришло в файле; подписи берём из `dictionaries.json`, а если его нет — из
встроенного словаря, а незнакомый код показываем как есть.

## Справочники

Три справочника заданы самим ТЗ, и их состав закрыт.

**Навык** — один у заявки, от одного до трёх у инженера:

| Код | Подпись по ТЗ |
|---|---|
| `local` | Локальные работы |
| `connect` | Работы на подключение и дозаказы |
| `emergency` | Аварийные работы |

Этот справочник ложится на выгрузку один в один — колонка «Тип заявки BK»:
«Локальная заявка» → `local`, «Подключение» и «Дозаказ» → `connect`,
«Глобальная проблема» → `emergency`. Классификация не выдумана нами, а взята из
учётной системы заказчика, и это стоит сказать вслух на защите.

**Тип транспортного средства** — один у инженера, у заявки только при наличии
ограничения:

| Код | Подпись по ТЗ |
|---|---|
| `car` | Автомобиль |
| `walk` | Пешеход |
| `bike` | Велосипед |
| `transit` | Общественный транспорт |

**Приоритет** — `normal` (обычная) и `urgent` (срочная). Прежнее числовое поле
`priority` остаётся как есть; новое `priority_class` говорит то же самое словами
ТЗ. Если движок его не прислал, правило вывода одно: `priority >= 2` — срочная.

Остальные справочники открытые: их состав задаёт выгрузка, а не мы.

**Класс заявки** (колонка «Тип заявки BK»): `connection` — подключение,
`addon` — дозаказ, `incident` — локальная заявка, `outage` — глобальная
проблема.

**Статус визита** (колонка «Статус BK»): `draft` — не отправлена, `sent` —
отправлена, `en_route` — в пути, `in_progress` — в работе, `done` — выполнена,
`cancelled` — отменена, `overdue` — просрочена. Эти семь значений — готовый
жизненный цикл визита, и именно по нему живёт интерфейс инженера.

**Технология** (колонка «Подключение»): `FMC`, `FTTB`, `GPON`. Открытый список.

**Оборудование**: `router`, `stb` (ТВ-приставка), `ont`, `cable`, `splitter`.
Открытый список; в выгрузке оборудование названо внутри типа работ («Роутер.
Замена техническим специалистом», «TVE/ENT. Замена приставки техником»).

## orders[]

| Поле | Тип | Значение |
|---|---|---|
| `order_class` | string \| null | класс заявки: `connection`, `addon`, `incident`, `outage` |
| `priority_class` | string \| null | `normal` \| `urgent` — приоритет словами ТЗ |
| `status` | string \| null | статус визита из справочника выше |
| `required_transport` | string \| null | код транспорта; `null` — ограничения нет |
| `required_equipment` | string[] \| null | коды оборудования, которое нужно везти |
| `tech` | string \| null | технология подключения |
| `gigabit` | bool \| null | гигабитное подключение |
| `contact` | object \| null | `{ "name": "…", "phone": "…" }` — кого искать на объекте |
| `locked_to` | string \| null | инженер, закреплённый диспетчером вручную |
| `assigned_by` | string \| null | `solver` \| `dispatcher` — кто назначил |
| `unassigned_reason` | object \| null | `{ "code": "…", "text": "…" }` — почему не назначена |

**`required_transport` пустой у большинства заявок, и это не пробел в данных.**
ТЗ говорит прямо: требуемый тип транспорта указывается только при наличии
такого ограничения. `null` означает «поедет кто угодно», а не «неизвестно».

**`locked_to` — это обещание, а не пожелание.** Диспетчер закрепил заявку за
человеком вручную; пересчёт обязан оставить её там, даже если это дороже. Если
движок не может выполнить закрепление, заявка уходит в неназначенные с причиной,
а не тихо переезжает к другому.

**`unassigned_reason` дублирует то, что и так объясняет `explain.json`, — и
дублирует намеренно.** Список заявок без инженера должен показывать причину
сразу, не подгружая ради одной строки файл на полтораста килобайт. Коды причин:

| `code` | Когда |
|---|---|
| `no_skill` | ни у кого нет нужного навыка |
| `no_vehicle` | ни у кого нет требуемого транспорта |
| `no_equipment` | ни у кого нет нужного оборудования |
| `no_time` | подходящие инженеры заняты в это время |
| `window_missed` | окно заявки не попадает ни в одну смену |
| `unreachable` | доехать вовремя не успевает никто |

`text` — та же причина human-фразой, готовой к показу: движок знает подробности,
которых нет в коде, и повторять его работу в вёрстке незачем.

## engineers[]

| Поле | Тип | Значение |
|---|---|---|
| `transport` | string \| null | тип транспортного средства, один |
| `status` | string \| null | `on_shift` \| `off_shift` \| `unavailable` |
| `team` | string \| null | бригада, как она названа в выгрузке: «Бригада Соколов» |
| `zone` | string \| null | участок приписки: «Восток», «Юго-Восток», «Центр» |
| `phone` | string \| null | рабочий телефон |
| `photo` | string \| null | путь к снимку |
| `position` | object \| null | `{ "lat": …, "lon": …, "at": 812 }` — где он сейчас |

**`transport` у инженера обязателен по смыслу, но по формату необязателен** —
движок 1.1 его не отдаёт. Пока поле пустое, ограничение по транспорту не
проверяется ни движком, ни интерфейсом: нечем.

**`status: unavailable` — это тот самый сценарий перепланирования из ТЗ.**
Инженер, у которого стоит этот статус, в план не попадает; его заявки
пересчитываются.

**`position` заполняется по ходу дня** и нужен двоим: карте — чтобы показать,
где бригада, и пересчёту — чтобы считать остаток дня от текущего места, а не от
офиса. Движок это уже умеет внутри, наружу не отдавал.

**`photo` раздаёт стенд, а не движок.** Поле описано здесь, чтобы, когда
настоящие снимки появятся, их некуда было не положить.

## routes[].stops[]

| Поле | Тип | Значение |
|---|---|---|
| `distance_km` | number \| null | пробег перегона до этой точки |
| `status` | string \| null | фактический статус визита |
| `fact` | object \| null | `{ "arrive": …, "start": …, "finish": … }` — как получилось |
| `late_probability` | number \| null | вероятность опоздать, 0…1 |

**`fact` против плановых `arrive`/`start`/`finish`.** Плановые времена — это то,
что обещал планировщик; `fact` — то, что отметил инженер в своём интерфейсе.
Расхождение этих двух рядов и есть «прогноз опозданий против факта»; пока
интерфейса инженера нет, `fact` пустой у всех.

**`late_probability` — не то же самое, что `risk`.** `risk` считается из запаса
по времени и детерминирован; вероятность опоздания приходит из симуляции, где
разыграны пробки, неявки и разброс длительностей. Визит может стоять с большим
запасом и всё равно быть хрупким.

## routes[].totals

| Поле | Тип | Значение |
|---|---|---|
| `distance_km` | number \| null | пробег всего маршрута |

## meta

| Поле | Тип | Значение |
|---|---|---|
| `engineers_used` | int \| null | сколько исполнителей получили хотя бы один визит |
| `distance_km_total` | number \| null | суммарный пробег плана |
| `baseline` | object \| null | тот же день базовым вариантом — для сравнения |

**`engineers_used` — первая обязательная метрика ТЗ.** Её можно посчитать и
самому, по длине `routes`, и интерфейс так и делает сейчас. Но метрика, которую
жюри будет сверять, должна приходить от того, кто её оптимизирует, а не
пересчитываться на другой стороне провода.

**`baseline` — вторая половина требования ТЗ «сравните с базовым вариантом».**
Это сводка, а не план целиком:

```jsonc
"baseline": {
  "solver": "greedy",              // чем считали базовый вариант
  "orders_assigned": 41,
  "engineers_used": 11,
  "distance_km_total": 214.8,
  "travel_minutes_total": 372
}
```

Полный базовый план, если он понадобится на карте, отдаётся обычным запросом
плана с указанием солвера: `GET /api/plan?day=1&solver=greedy`. Форма ответа —
та же самая, поэтому карта и таймлайн показывают его без единой правки.

## meta.replan

Блок уже существует и уже разводит три исхода — `rescued`, `kept`, `lost` (см.
`SERVER.md`). 1.2 не заводит рядом второй такой же, а добавляет к нему два поля.

```jsonc
"replan": {
  "at": 820,
  "event": {                        // что именно случилось — новое поле
    "type": "urgent",               // urgent | cancel | disabled | delayed
    "order_id": "R0087",            // для срочной заявки и отмены
    "engineer_id": null             // для ЧП с инженером
  },
  "incident": {
    "rescued": ["R0031"],           // подхвачены другим инженером
    "kept":    ["R0044"],           // остались там же
    "lost":    ["R0052"],           // выпали из плана
    "moved":   ["R0019"]            // сменили инженера или место — новое поле
  }
}
```

**`moved` — новое и нужное.** Сегодня пересчёт честно говорит, кого спасли и
кого потеряли, но молчит о тех, кто просто переехал к другому инженеру. Для
диспетчера это главный вопрос после ЧП: не «сколько потеряли», а «что теперь
поменялось в моих маршрутах». Считать это на стороне интерфейса, сличая два
плана, можно — но тогда два места будут по-разному отвечать на один вопрос.

**`event` нужен затем, что сегодня о событии приходится догадываться** по тому,
какие поля заполнены: есть `incident` — значит, ЧП с инженером, пришли
`urgent_ids` — значит, авария. Пока событий три, это терпимо; журнал событий за
день на этом уже не построить.

**`type: "cancel"` — отмена заявки.** Из трёх событий ТЗ движок сегодня умеет
два с половиной: срочная заявка и недоступность инженера сделаны, отмена
получается сама собой, если не подавать заявку на вход, но отдельного вызова под
неё нет. В 1.2 она названа явно, чтобы интерфейсу было что вызвать.

## explain.json

Словарь вердиктов пополняется двумя значениями:

| `verdict` | Значение |
|---|---|
| `no_vehicle` | у инженера не тот тип транспорта |
| `no_equipment` | у инженера нет нужного оборудования |

Остальные пять — без изменений.

## orders.json и engineers.json — входные формы

Четыре формы контракта 1.1 описывают **результат**: план, объяснение, симуляцию,
смены. Чего в контракте не было никогда — это **входа**: движок до сих пор
получал день от собственного генератора, и описывать было нечего.

С появлением настоящей выгрузки вход понадобился: ТЗ требует «загружать готовые
тестовые данные из CSV или JSON», а набор, собранный из выгрузки заказчика,
надо чем-то передать движку. Отсюда две формы. Обе лежат в
`dataset/out/<зона>/` и собираются скриптом `dataset/build.py`.

```jsonc
{
  "schema": "1.2",
  "kind": "orders",
  "meta": {
    "date": "2026-08-17",
    "zone": "Восток",
    "time_format": "minutes_from_midnight",
    "distance_units": "km",
    "source": "выгрузка «Билайн Бизнес» за 17.08.2026"
  },
  "orders": [ /* ровно те же поля, что у orders[] в plan.json */ ]
}
```

`engineers.json` устроен так же и содержит `engineers[]` в том же виде, что и
план. Совпадение полей — не совпадение, а условие: интерфейс, который умеет
показать заявку из плана, обязан уметь показать её же до планирования, иначе
экран загрузки данных пришлось бы писать второй раз с нуля.

Отличия входа от результата ровно два, и оба очевидные: у заявки `assigned_to`
всегда `null`, а маршрутов нет вовсе — их ещё не построили.

Рядом лежит `orders.csv` — тот же набор плоской таблицей, с колонками, которые
понимает загрузка заявок в интерфейсе. Он нужен не движку, а демонстрации:
это самый короткий способ показать, что сервис читает настоящую выгрузку, а не
только собственные фикстуры.

## dictionaries.json — пятая форма

Необязательная. Нужна затем же, зачем контракт запрещает зашивать справочники в
вёрстку: состав кодов задают данные, а подписи к ним должны приходить оттуда же,
а не жить в коде интерфейса, где их правит другой человек и в другой день.

```jsonc
{
  "schema": "1.2",
  "kind": "dictionaries",
  "skills":        { "local": "Локальные работы", "connect": "Работы на подключение и дозаказы", "emergency": "Аварийные работы" },
  "transports":    { "car": "Автомобиль", "walk": "Пешеход", "bike": "Велосипед", "transit": "Общественный транспорт" },
  "order_classes": { "connection": "Подключение", "addon": "Дозаказ", "incident": "Локальная заявка", "outage": "Глобальная проблема" },
  "statuses":      { "draft": "Не отправлена", "sent": "Отправлена", "en_route": "В пути", "in_progress": "В работе", "done": "Выполнена", "cancelled": "Отменена", "overdue": "Просрочена" },
  "work_types":    { "…": "…" },
  "equipment":     { "router": "Роутер", "stb": "ТВ-приставка" },
  "techs":         { "FMC": "FMC", "FTTB": "FTTB", "GPON": "GPON" }
}
```

Если формы нет, интерфейс берёт подписи из встроенного словаря, а незнакомый код
показывает как есть. Ни один экран от её отсутствия не ломается.

## Что гарантируется дополнительно

К списку гарантий из 1.1 добавляются четыре, и все — при условии, что поле
вообще пришло:

- `unassigned_reason` заполнен у каждой заявки из `unassigned` и пуст у всех
  остальных;
- `locked_to`, если он не пуст, совпадает с `assigned_to` — либо заявка лежит в
  `unassigned` с причиной, объясняющей, почему закрепление не выполнено;
- `distance_km` на маршруте равен сумме `distance_km` его остановок, а
  `meta.distance_km_total` — сумме по маршрутам;
- `meta.engineers_used` равен числу элементов в `routes`.

## Разделение работ

Кто что делает по каждому полю. Столбец «источник» отвечает на один вопрос:
откуда значение возьмётся на демонстрации, если движок его ещё не отдаёт.

| Поле | Источник | Кто делает |
|---|---|---|
| `required_transport`, `engineers[].transport` | выгрузка не содержит — синтезируем при сборке набора | движок проверяет, интерфейс показывает |
| `distance_km` во всех трёх местах | дорожная сеть движка, поле `road_km` уже есть | движок |
| `meta.engineers_used`, `meta.baseline` | жадный солвер в движке уже написан | движок |
| `order_class`, `status`, `tech`, `gigabit` | выгрузка, колонки «Тип заявки BK», «Статус BK», «Подключение», «Гигабитное подключение» | данные |
| `priority_class` | выводится из класса заявки | данные |
| `required_equipment` | выводится из типа работ | данные |
| `contact` | выгрузка не содержит — синтезируем | данные |
| `locked_to`, `assigned_by` | ставит диспетчер в интерфейсе | интерфейс, движок соблюдает |
| `stops[].fact`, `stops[].status` | отмечает инженер в своём интерфейсе | интерфейс |
| `late_probability` | симуляция движка, `fragile` уже считается по заявкам | движок |
| `engineers[].position` | движок знает внутри при пересчёте остатка дня | движок |
| `unassigned_reason` | движок знает причину, `explain` её уже формулирует | движок |

# Живой бэкенд вместо фикстур

Фикстуры в `day-01/`, `day-02/`, `day-07/` никуда не деваются — на них
удобно верстать. Но интерфейс, где кнопка «авария» ничего не делает,
на защите смотрится плохо. Поэтому в стенде есть сервер, отдающий ровно
те же четыре формы, только вживую, и умеющий пересчитывать день.

Переход с фикстур на сервер — это замена одной строки:

```js
fetch('day-01/plan.json')            // было
fetch('/api/plan?day=1')             // стало
```

Формат ответа тот же самый, `CONTRACT.md` продолжает действовать.

## Запуск

Нужен Python 3.10+ и папка `vrptw/` из стенда. Ничего ставить не нужно
сверх `numpy` и `scipy` — сервер написан на стандартной библиотеке.

```bash
cd <папка, где лежит vrptw/>
pip install numpy scipy
python3 -m vrptw.server
```

Первый запуск считает день (около минуты) и кладёт результат в
`.vrptw-cache/`, дальше поднимается за пару секунд. Сервер слушает
`http://localhost:8000`, описание всех путей — на `http://localhost:8000/api`.

Проверить, что всё живо, не открывая браузер:

```bash
python3 -m vrptw.server check
```

## Пути

**`day` — это строка, а не число.** Либо имя зоны обслуживания
заказчика: `восток`, `юго-восток`, `югоцентр` — настоящая выгрузка за
17.08.2026. Либо номер синтетического дня, `1`…`30`, как раньше. В URL
имя зоны надо процентно кодировать (`encodeURIComponent`), браузер
сделает это сам через `fetch`. Неизвестный идентификатор вернёт 400 с
понятным текстом, а не посчитается.


| Запрос | Что вернёт |
|---|---|
| `GET /api/plan?day=1` | маршруты, карта, таймлайн — то же, что `plan.json` |
| `GET /api/explain?day=1` | панель «почему так» |
| `GET /api/simulation?day=1` | сводка дня и хрупкие визиты |
| `GET /api/shifts?day=1` | график выхода: спрос против смен |
| `GET /api/day?day=1` | все четыре формы одним ответом |
| `GET /api/days` | какие дни готовы, какие можно попросить, и список зон |
| `GET /api/plan?day=восток` | то же, но на **настоящих данных заказчика** |
| `GET /api/baseline?day=восток` | базовый вариант из ТЗ — для обязательного сравнения |
| `GET /api/tuned?day=1` | план того же дня по **подобранному** графику смен |
| `GET /api/replan?day=1&at=820&urgent=2` | пересчёт: аварии в 13:40 |
| `GET /api/replan?day=восток&at=820&urgent=2&urgent_near=E03` | аварии «у кого на участке»: рядом с тем, где E03 сейчас |
| `GET /api/replan?day=восток&at=820&urgent=2&base=run-…` | от открытого расчёта: его план, переменные и журнал; то же `base` у событий, состояния, журнала и «сколько людей» |
| `GET /api/replan?day=1&at=820&cancelled=R0038` | абонент отказался от визита |
| `GET /api/replan?day=восток&at=720&cancelled=auto` | то же на зоне: движок сам выберет заявку |
| `GET /api/replan?day=1&at=820&disabled=E03` | инженера сегодня не будет |
| `GET /api/replan?day=восток&at=720&disabled=auto` | то же на зоне: самый занятой в этот момент |
| `GET /api/replan?day=1&at=820&delayed=E03:40` | инженер задержится на 40 минут |
| `POST /api/replan` | то же телом `{day, at, urgent, urgent_near, cancelled, seconds, run, disabled, delayed, source}` |
| `POST /api/event` | сообщить, что случилось на самом деле |
| `GET /api/state?day=1&at=820` | что движок думает о дне: выполнено, сорвано, кто где |
| `GET /api/journal?day=1` | всё сообщённое плюс сводка |
| `GET /api/orders?day=1` | заявки, поступившие за день |
| `GET /api/settings` | семь настроек: значения, пределы, описания |
| `POST /api/settings` | поменять их |
| `POST /api/journal/reset` | забыть сообщённое и вернуться к утреннему плану |
| `POST /api/journal/adopt` | «Принять» показанный пересчёт от журнала: `{day, token}`, ярлык — `meta.replan.adopt_token`; журнал изменился после показа — `409` |

`day` — номер дня от 1 до 30. Разные номера дают разные дни: удобно,
чтобы вёрстка не оказалась подогнанной под один набор.

## Пересчёт — то, ради чего сервер и нужен

```js
const r = await fetch('/api/replan?day=1&at=820&urgent=2').then(r => r.json())
```

`at` — момент в минутах от полуночи (820 = 13:40), `urgent` — сколько
аварий приходит в этот момент. В ответе обычный `plan`, но на **остаток
дня**, плюс блок `meta.replan`:

```jsonc
"replan": {
  "at": 820,
  "solve_seconds": 1.5,        // сколько думал планировщик
  "stability": 1.0,            // доля визитов, сохранивших исполнителя
  "urgent_ids": ["U00", "U01"],
  "urgent_near": null,         // у кого на участке пришла авария; null — по зоне
  "urgent_assigned": 2,        // сколько аварий влезло в план
  "done_before": ["R0004"],    // что уже выполнено к этому моменту
  "failed_before": {"R0011": "no_show"},   // и что уже сорвалось
  "assigned_now": 24,          // столько визитов в новом плане
  "assigned_as_is": 22         // столько было бы, если не пересчитывать
}
```

Разница `assigned_now` против `assigned_as_is` — это и есть цена
пересчёта в визитах, её стоит показать на экране. `stability` —
вторая цифра для показа: план не перетасовывает людей, которым уже
сказали ехать.

Один и тот же `run` даёт один и тот же ход дня, поэтому демо
воспроизводится: нажали второй раз — получили то же самое. Меняете
`run` — получаете другой случайный день.

## Три события пересчёта, и все три разные

ТЗ называет три события: срочная заявка, отмена заявки, недоступность
инженера. У нас недоступность разделена надвое — «не будет вовсе» и
«задержится», — потому что стоят они разного.

```js
fetch('/api/replan?day=1&at=820&urgent=2')          // появились срочные
fetch('/api/replan?day=восток&at=720&cancelled=auto')  // абонент отказался
fetch('/api/replan?day=восток&at=720&disabled=auto')   // сегодня его не будет
fetch('/api/replan?day=восток&at=720&delayed=auto:40') // задержится на 40 минут
```

`cancelled` принимает несколько номеров через запятую. Отменить можно
только то, что ещё не выполнено; отмена вместе с ЧП по инженеру
отвергается — ТЗ просит показать одно событие, и мерить их вместе значит
не понять, что дало эффект.

На экране они должны выглядеть по-разному, потому что и стоят разного:

| | во что обходится дню | что возвращает пересчёт |
|---|---|---|
| выбыл до конца дня | −3,8 визита утром | **+2,9** — жать обязательно |
| задержался на 40 минут | −0,3 визита | +0,1…+0,3 — незачем |
| абонент отказался | освобождает ёмкость | сколько работы влезло в освободившееся |

Прокол буферы в маршруте съедают сами. Система, которая перетасовывает
бригаду из-за сорокаминутной задержки, хуже той, что не делает ничего:
людям уже позвонили и сказали ехать. Поэтому диспетчеру нужно дать
выбрать, что именно случилось, а не одну кнопку «ЧП».

В ответе появляется блок `meta.replan.incident` — и в нём то, что стоит
показать прямо на экране:

```jsonc
"incident": {
  "kind": "disabled",          // disabled | delayed | cancelled
  "engineer_id": "E04",
  "minutes": null,             // для delayed — на сколько задержался
  "pending_was": ["R0002", "R0025", "R0029", "R0044"],  // было у него впереди
  "rescued":     ["R0002", "R0025", "R0029", "R0044"],  // подхватили другие
  "kept":        [],           // остались за ним (при задержке — обычное дело)
  "lost":        [],           // не влезли никуда
  "stability_others": 0.941    // доля НЕ причастных визитов, сохранивших исполнителя
}
```

Три списка — `rescued`, `kept`, `lost` — в сумме дают ровно
`pending_was`, ничего не теряется. На карте это три цвета.

У отмены вопрос другой. Там не «куда делись его визиты», а «что купила
освободившаяся ёмкость», и блок выглядит иначе:

```jsonc
"incident": {
  "kind": "cancelled",
  "engineer_id": null,
  "order_ids": ["R0038"],      // что отменили
  "freed_minutes": 65,         // сколько работы ушло из дня
  "picked_up": ["R0011"],      // что влезло вместо неё
  "picked_up_count": 1,
  "stability_others": 0.97
}
```

`picked_up` — это заявки, которых утренний план не вмещал вовсе, а
теперь вместил. Именно их стоит подсветить: диспетчер отменил один визит
и получил взамен другой, и это видно числом, а не на слово.

Отменённая заявка исчезает из дня целиком: её нет ни в маршрутах, ни в
`unassigned`. Записывать её в невыполненные было бы враньём — её никто и
не просил выполнять.

`stability_others` считается только по инженерам, которых ЧП не
касалось: визиты выбывшего обязаны сменить исполнителя, ставить это в
упрёк пересчёту нечестно. Именно это число показывает, что система не
разворошила всю бригаду ради одного человека.

Так выглядит разница на дне 1, инженер E04, 13:40:

| | подхватили другие | осталось за ним | назначено против «как ехали» |
|---|---|---|---|
| `disabled=E04` | 4 из 4 | 0 | 23 против 18 |
| `delayed=E04:40` | 1 из 4 | 3 | 24 против 21 |

Видно, что система реагирует соразмерно: при выбытии разбирает его
маршрут целиком, при задержке трогает один визит и не касается никого
постороннего.

## Память: движок теперь можно поставить в известность

Раньше её не было вовсе, и это правильно подметил Антон. Состояние дня
на момент пересчёта движок разыгрывал костями: параметр `run` выбирал
случайную траекторию, и сказать «этот визит закрыт, а сюда не пустили»
было некуда. Перезагрузил страницу — всё вернулось в начало.

Теперь есть журнал. Диспетчер сообщает события, движок из них собирает
состояние дня и пересчитывает план от реального положения дел.

```js
// закрыли визит
await fetch('/api/event', {method: 'POST', headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({day: 1, kind: 'done', order: 'R0012', at: 754})})

// не застали абонента
{day: 1, kind: 'failed', order: 'R0031', at: 812, reason: 'no_show'}

// инженера сегодня не будет / задержится / вернулся
{day: 1, kind: 'engineer_out', engineer: 'E03', at: 820}
{day: 1, kind: 'engineer_delayed', engineer: 'E05', at: 820, minutes: 40}
{day: 1, kind: 'engineer_back', engineer: 'E05', at: 900}

// поступила новая заявка
{day: 1, kind: 'order_new', at: 780, lat: 55.7521, lon: 37.5904,
 work_type: 'repair', window_start: 780, window_end: 1020,
 est_minutes: 45, priority: 2, address: 'Ленинский проспект, 32'}
```

**Про новую заявку.** Обязательны только `lat` и `lon`: интерфейс знает,
куда ехать, а движок не геокодирует и в момент показа в сеть не лезет.
Остальное можно не называть — окно возьмётся трёхчасовым от момента
звонка, длительность из справочника работ, приоритет аварийный. Свой
номер заявки можно передать в `order`, иначе движок выдаст `N0000`,
`N0001` и так далее.

В ответе на пересчёт появляются две строки: `reported_ids` — что
сообщили и ещё не пристроили, `reported_assigned` — сколько из них
влезло. Повторный пересчёт заявку не задваивает: после первого она уже
числится за инженером.

Причины срыва — те же, что различает симулятор: `no_show`, `no_access`,
`missed_window`, `cancelled`. Одна на всех терминология: отчёт диспетчера
и внутренний замер говорят на одном языке.

**Пересчёт от реальности** — тот же путь, только с `source=journal`:

```js
const r = await fetch('/api/replan?day=1&at=820&urgent=2&source=journal')
```

Без этого параметра всё работает как раньше: состояние разыгрывается по
`run`. Это осталось для демо без диспетчера и для замеров, где день надо
проиграть сотни раз. Переключение сделано явным нарочно — чтобы никто
случайно не измерил качество планировщика на выдуманных событиях.

При `source=journal` не нужно передавать `disabled` и `delayed`: если о
человеке уже сообщили, движок сам это учтёт.

**Что показать на экране** — `GET /api/state?day=1&at=820`:

```jsonc
{
  "done": ["R0012", "R0044"],
  "failed": {"R0031": "no_show"},
  "pending": {"E00": ["R0058", "R0071"], "E01": [...]},
  "position": {"E00": {"node": 214, "free_at": 812}},
  "summary": {
    "done": 2, "failed": 1, "failed_by_reason": {"no_show": 1},
    "new_orders": 1,
    "absent": ["E03"], "delayed": {"E05": 40},
    "assigned_now": 57, "pending_now": 54
  }
}
```

Список поступивших заявок целиком — `GET /api/orders?day=1`: там же
видно, какие из них ещё никому не отданы (`unplaced`).

**Сброс для демо:** `POST /api/journal/reset` с телом `{"day": 1}` —
день возвращается к утреннему плану. Прогнали сценарий, показали, сбросили,
показываете снова.

Журнал переживает перезапуск сервера: лежит файлом в `.vrptw-journal/`.

**Отчитаться дважды по одной заявке нельзя** — придёт 400 с объяснением.
Это нарочно: журнал единственное место, где движок узнаёт о реальности, и
мусор в нём тихо испортил бы все последующие пересчёты. Переиграть можно
только сбросом дня.

Весь путь — отчёт, состояние, пересчёт, сброс — проверяется в
`python3 -m vrptw.server check`.

## Настройки: те самые семь ручек

Ровно те, о которых договаривались. Больше движок наружу не отдаёт
ничего — бюджет поиска, размер выбивания, шум пересборки подобраны
замерами, и любая их правка обесценит все измеренные числа.

```js
const s = await fetch('/api/settings').then(r => r.json())
```

Приходит всё, что нужно для экрана: текущее значение, значение по
умолчанию, пределы и человеческое описание.

```jsonc
"buffer_step": {
  "value": 16.0, "default": 16.0, "min": 0.0, "max": 120.0,
  "about": "прирост запаса на каждый следующий визит, минут"
}
```

| настройка | что делает |
|---|---|
| `churn_penalty` | сколько платим за то, чтобы при пересчёте не дёргать людей |
| `duration_factor` | насколько закладываться, что работа затянется |
| `buffer_base` | запас до закрытия окна для первого визита |
| `buffer_step` | и прирост запаса на каждый следующий |
| `balance_weight` | насколько ровно раскладывать день между людьми |
| `risk_high` | запас меньше этого — красным |
| `risk_medium` | меньше этого — жёлтым |

Менять — телом с любым подмножеством:

```js
await fetch('/api/settings', {method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({risk_high: 30, risk_medium: 60})})
// → {"changed": ["risk_high", "risk_medium"], "settings": {...}}
```

**Первые пять меняют сам план**, последние две — только подсветку на
экране. Поэтому после правки первых пяти день пересчитывается: кэш
сбрасывается, и следующий `/api/plan` придёт через несколько секунд, а не
мгновенно. Это нормально, но спиннер лучше показать.

Настройки лежат файлом и переживают перезапуск.

**Опечатка в имени и значение за пределом отбиваются с 400 и понятным
текстом** — не молча. `risk_high` не может быть больше `risk_medium`:
красным подсвечивают то, что впритык сильнее жёлтого.

### `churn_penalty` — живой контрол, а не настройка компании

Его можно передать прямо в пересчёт, не трогая общие настройки:

```js
fetch('/api/replan?day=1&at=820&urgent=2&churn_penalty=250')
```

Это то, что диспетчер двигает на экране инцидента и сразу видит, во что
обходится стабильность. В ответе он приходит обратно в
`meta.replan.churn_penalty`, чтобы экран не гадал, что именно применилось.

Замер, если понадобится подпись к ползунку: при нуле план сохраняет
исполнителя у половины визитов, при 40 — у 87–95%, дальше 100 почти не
растёт, и покрытие при этом не меняется нигде.

## Интерфейс с того же адреса

Если положить собранный фронт в папку `web/` рядом с `vrptw/`, сервер
начнёт раздавать её сам:

```
проект/
├── vrptw/
└── web/
    └── index.html
```

Тогда всё открывается с `http://localhost:8000`, и вопрос CORS не
возникает вовсе. Это самый надёжный вариант для защиты, где браузер
чужой и настроек в нём не поменять.

Если фронт удобнее держать на своём dev-сервере (Vite и подобное) —
тоже работает: сервер отдаёт `Access-Control-Allow-Origin: *`, запросы
с другого порта проходят.

## Что учесть

**Первый запрос по новому дню считается несколько секунд.** Дни 1, 2, 7
можно прогреть заранее: `python3 -m vrptw.server 8000 1,2,7`. Остальные
считаются по требованию и потом лежат в кэше.

**`/api/tuned` — самый медленный, около минуты на новый день.** Он
подбирает график смен настоящим солвером. После первого раза — мгновенно.

**Пересчёт занимает полторы секунды** — это не задержка сети, это
работа планировщика. Полторы секунды на экране лучше показать честно
(спиннер с надписью «пересобираю маршруты»), чем прятать: это ровно та
цифра, которой мы хвалимся.

**Кэш живёт в `.vrptw-cache/`.** Правку движка он замечает сам: в имени
файла стоит отпечаток содержимого кода, и после правки солвера день
пересчитывается, а не отдаётся вчерашним. Удалять руками больше не надо;
`&fresh=1` остаётся, если нужен пересчёт при том же коде. Нынешний
отпечаток отдаёт `GET /api/health` полем `code` — по нему видно, одну ли
версию движка вы смотрите.

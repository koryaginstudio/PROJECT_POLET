# Стенд планировщика выездов

День монтажников на настоящей карте Москвы: адреса домов из
OpenStreetMap, дороги и время в пути из OSRM, симулятор исполнения с
каскадом опозданий и два планировщика на одном интерфейсе.

## Что нужно

Python 3.10 или новее, `numpy` и `scipy`. Больше ничего.

```bash
tar xzf vrptw_stend.tar.gz
cd <папка, где лежит vrptw/>
pip install numpy scipy
python3 -m vrptw.selfcheck
```

`selfcheck` проходит весь путь за полминуты: граф, генерация дня, оба
планировщика с проверкой инвариантов, симуляция, подбор смен, выгрузка для
интерфейса и проверка контракта. Если он зелёный — всё собрано правильно.

Команды запускаются **из папки, внутри которой лежит `vrptw/`**, а не из
самой `vrptw/`.

## Принцип

Планировщик видит только оценки (`est_minutes`, окна, SLA). Насколько
работа затянется, будет ли абонент дома, пустят ли в подъезд — живёт в
распределениях `WorkType` и **разыгрывается симулятором заново в каждом
прогоне**, а не записывается в заявку заранее. Иначе Монте-Карло меряет
одну лишь дорожную неопределённость.

Главная метрика — **покрытие дня**: доля выполненных из всех поступивших
заявок. Доля выполненных *из запланированных* выглядит внушительнее, но
почти не зависит от планировщика — её определяют неявки.

## Карта

Москва настоящая. Шестьсот адресов домов из OpenStreetMap по всем
пятидесяти районам, время в пути между ними — из маршрутизатора OSRM по
реальному графу дорог, линия на карте — настоящая ломаная по улицам.

Пробок OSRM не знает: он считает по свободной дороге. Поэтому почасовой
профиль пробок остался наш, и применяется он не одинаково ко всем
поездкам — от пары точек берётся то, насколько поездка меняет удаление от
центра. Едешь «внутрь» — поездка радиальная и встаёт сильнее, идёшь по
дуге на том же радиусе — кольцевая. Сверка с прежней выдуманной моделью:

| маршрут | км по дорогам | 13:00 | 18:00 |
|---|---|---|---|
| Митино → Марьино | 44,3 | 55 мин | 97 мин |
| Ясенево → Медведково | 50,9 | 51 мин | 92 мин |
| Хамовники → Таганский | 8,9 | 19 мин | 36 мин |

Проверить самому: `python3 -m vrptw.core.osm check` покажет те же
поездки на обеих сетях рядом.

**Интернет не нужен.** Адреса, матрица времени и геометрия маршрутов
лежат в репозитории и весят два с половиной мегабайта. Пересобрать их
можно (`python3 -m vrptw.core.osm fetch`), но на защите это не
понадобится.

Синтетическая радиально-кольцевая модель никуда не делась и осталась
запасным вариантом: ей не нужны ни файлы, ни сеть. Включается
переменной `VRPTW_SYNTHETIC_MAP=1`. Все числа ниже сняты на настоящей
карте.

## Запуск

Время указано для двух ядер; на нормальном ноутбуке будет заметно быстрее.

| Команда | Время | Что покажет |
|---|---|---|
| `python3 -m vrptw.selfcheck` | 30 с | всё ли собрано правильно |
| `python3 -m vrptw.diagnose` | 1 мин | во что упирается день |
| `python3 -m vrptw.bench 12` | 3 мин | парное сравнение планировщиков |
| `python3 -m vrptw.shiftbench proxy` | 2 мин | можно ли верить прокси спроса |
| `python3 -m vrptw.validate` | 8 мин | held-out, проверка буфера и сходимость LNS |
| `python3 -m vrptw.validate buffer` | 3 мин | буфер против буфера на новых днях |
| `python3 -m vrptw.validate converge` | 3 мин | зависит ли результат от бюджета поиска |
| `python3 -m vrptw.shifts` | 5 мин | вклад расписания смен |
| `python3 -m vrptw.tune` | 5 мин | подбор буфера |
| `python3 -m vrptw.shiftceiling` | 10 мин | сколько недобирает прокси |
| `python3 -m vrptw.shiftbench` | 12 мин | подбор смен против ручного веера |
| `python3 -m vrptw.replanbench` | 8 мин | пересчёт внутри дня против его отсутствия |
| `python3 -m vrptw.replanbench churn` | 10 мин | чем платим за стабильность плана |
| `python3 -m vrptw.optimumbench full` | 5 мин | разрыв до оптимума на полном дне |
| `python3 -m vrptw.optimumbench` | 20 мин | разрыв до оптимума на пяти размерах |
| `python3 -m vrptw.dropoutbench` | 8 мин | инженер выбыл до конца дня |
| `python3 -m vrptw.dropoutbench flat` | 8 мин | то же при проколе на 40 минут |
| `python3 -m vrptw.balancebench` | 6 мин | чем платим за равномерную загрузку |
| `python3 -m vrptw.balancebench asis` | 6 мин | то же на утренних сменах |
| `python3 -m vrptw.balancebench shifts` | 3 мин | равномерность как функция расписания |
| `python3 -m vrptw.stress` | 25 мин | держится ли всё на других размерах дня |
| `python3 -m vrptw.stress load` | 20 мин | то же при перекосе по загрузке |
| `python3 -m vrptw.stress edge` | 1 мин | вырожденные случаи: один инженер, одна заявка |

Выгрузка данных для интерфейса:

```bash
python3 -m vrptw.export 1 fixtures          # день 1 в папку fixtures/
python3 -m vrptw.validate_fixtures fixtures # проверка контракта
```

Живой бэкенд вместо статичных файлов — тот же контракт, но с пересчётом
внутри дня по запросу:

```bash
python3 -m vrptw.server        # http://localhost:8000, описание на /api
python3 -m vrptw.server check  # постучаться во все пути и сверить контракт
```

Сверх четырёх форм сервер умеет пересчитывать день по запросу — в том
числе на ЧП с инженером:

```bash
curl 'localhost:8000/api/replan?day=1&at=820&urgent=2'          # две аварии в 13:40
curl 'localhost:8000/api/replan?day=1&at=820&disabled=E03'      # сегодня его не будет
curl 'localhost:8000/api/replan?day=1&at=820&delayed=E03:40'    # задержится на 40 минут
```

Выбытие и задержка — намеренно разные запросы: замер говорит, что жать
пересчёт стоит в первом случае и почти незачем во втором. Подробности —
в `frontend_kit/SERVER.md`.

Каждый замер печатает доверительные интервалы по парному сравнению.
Число без интервала ничего не значит: разброс между днями больше, чем
разница между планировщиками.

**Числа не зависят от вашей машины.** Бюджет поиска в замерах задан не
секундами, а числом шагов LNS: секунда у каждого своя, шагов у всех
поровну. Секунды печатаются рядом — это latency-обещание, а не единица
измерения качества. Продукт при этом живёт по секундам: в диспетчерской
важна задержка ответа, и сервер считает именно так.

Убедиться, что бюджет вообще ни на что не влияет, проще всего по таблице
сходимости: `python3 -m vrptw.validate converge` показывает, что после
двухсот шагов покрытие уже не меняется, а восемь секунд боевого солвера —
это полторы тысячи шагов.

## Что стоит проверить руками

**Числа не подогнаны под удачные дни.** `bench` принимает число дней:
`python3 -m vrptw.bench 20` возьмёт другой набор. Доверительный интервал
должен остаться примерно тем же.

**Параметры не подогнаны под замер.** Буфер подбирался на днях 1–6,
`validate` меряет на днях 13–30 — тех, которых при настройке не было.

**Буфер зависит от расписания смен, и это меняет постановку.** Подбор
буфера на одном расписании уводит в минус на другом, поэтому
`validate buffer` меряет его сразу на двух, парно, на днях 13–30:

| расписание | буфер 0 | 16 | 30 | 45 |
|---|---|---|---|---|
| как есть | −0,00 ± 0,25 | рабочий | +0,61 ± 0,30 | **+0,88 ± 0,42** |
| веер | +0,16 ± 0,64 | рабочий | −0,50 ± 0,50 | **−3,82 ± 0,82** |

Буфер полезен ровно настолько, насколько остра нехватка рук. При
утренних сменах работы вдвое больше ёмкости — лишний визит всё равно
почти наверняка сорвётся, и выгоднее защищать уже поставленные. При
веере рук хватает, маршруты длиннее, и требование «запас 45·√позиция» на
девятой позиции вычёркивает визиты, которые прошли бы. Потолок над
буфером компромисс не снимает, а только двигает по той же кривой —
проверено отдельно.

Ниже 16 обе кривые плоские, выше — расходятся. Поэтому взято 16:
единственная точка, безопасная в обоих режимах. И поэтому же
`buffer_step` вынесен в настройки компании — развёртывание, которое
остаётся на утренних сменах, может поднять его само.

**План не жульничает.** `Plan.check_invariants` проверяется в каждом
замере: заявка не назначается дважды, старт не выходит за окно, финиш не
выходит ни за смену, ни за жёсткую границу дня, инженер не раздваивается.
Главное там — последнее: **время в пути пересчитывается по дорожной сети
на тот час, в который инженер выезжает, и сверяется с тем, что записано в
плане**. Без этого плану ничто не мешает объявить дорогу короче, чем она
есть, и получить красивое покрытие из воздуха. Уберите проверку — увидите,
что она не декоративная: на ней уже поймался ручной профиль смен, сажавший
последнего инженера на смену до 22:00.

**Планировщик не подглядывает в будущее.** Полей с фактическим исходом в
заявке нет вовсе: `selfcheck` это проверяет отдельно. Симулятор
разыгрывает неявку и длительность сам, в каждом прогоне.

**Симуляция даёт живой разброс.** `sd` должен быть около 2 при 55 визитах.
Если он меньше единицы — случайность где-то зафиксирована, и все выводы
о хрупкости плана недействительны.

**Поиск не вырождается.** Ruin & recreate имеет смысл, только если
пересборка может дать не то же самое, что в прошлый раз. Заявке с
единственным возможным местом раньше присваивалось бесконечное
сожаление — а бесконечность нельзя пошевелить шумом, и на маленьких
днях все итерации возвращали одно решение. Теперь сожаление конечно, а
пересборка рандомизирована (`Params.noise`). Проверить просто: поставьте
`noise=0` и запустите `optimumbench` — на дне 20/3 план станет хуже
оптимума на заявку.

**Быстрая версия солвера равна медленной.** `improved.py` и `fast.py` —
один алгоритм, второй переписан на инкрементальных пересчётах. При
нулевом бюджете LNS они обязаны давать один и тот же план визит в визит;
`selfcheck` проверяет это на каждом запуске — и не на голых параметрах,
а на четырёх наборах: без штрафов, со штрафом за неравномерность, со
штрафом за смену исполнителя и с обоими сразу. Продакшен считает именно
с ними, поэтому сверять только нули бессмысленно. Заодно проверяется,
что каждый штраф вообще меняет план: сверка на параметре, который ни на
что не влияет, ничего и не доказывает. Иначе замеры мерили бы один
солвер, а объяснения относились бы к другому.

## Результат

Покрытие дня — доля выполненных из 80 заявок. 12 дней, парное сравнение.

| | Жадный | Улучшенный |
|---|---|---|
| Смены как есть | 59,6% | 66,5% |
| Смены веером вручную | 68,5% | 78,5% |
| Смены подобраны | — | **80,3%** |

Вклад алгоритма **+6,4 ± 1,4 п.п.**, вклад расписания смен +12,0 ± 2,0
(с автоподбором +13,9 ± 1,9). Held-out на днях 13–30: **+8,9 ± 1,2**.

Расстановка смен даёт вдвое больше, чем алгоритм маршрутизации, и эффекты
складываются, а не конкурируют.

Разрыв до оптимума **ноль там, где оптимум доказан**. На пяти размерах
от 20 до 60 заявок HiGHS доказал оптимум в 8 случаях из 15 — и во всех
восьми наш план ему равен. Ещё в шести случаях наш план за 8 секунд
оказался лучше того, что HiGHS нашёл за полторы минуты.

На полном дне из 80 заявок точный решатель больше не помощник: за четыре
минуты он находит 11 визитов против наших 58 и не успевает прижать
верхнюю границу — она остаётся на 64. Формально разрыв до неё 9,4%, но
это расстояние до недоказанной границы, а не до оптимума, и настоящий
разрыв меньше. На выдуманной сети граница на полном дне сходилась; с
настоящими дорогами задача для MILP стала заметно тяжелее. Честный вывод
такой: **точный оптимум работает как детектор ошибок на малых днях, а не
как оценка качества на больших** — ровно так он и был задуман.

Пересчёт внутри дня: две аварии в 13:40 с трёхчасовым окном. Без пересчёта
они уезжают на завтра, с пересчётом выполняется 1,8 из 2, и всего за день
на 4,1 визита больше. Новый план готов за 1,5 секунды и сохраняет 87%
назначений — инженеры, которым уже сказали ехать, продолжают ехать.
Промедление стоит дёшево: пересчёт через час вместо немедленного не
теряет ничего (−0,2 визита, в пределах шума). Ценность здесь в самом
факте пересчёта, а не в секундах реакции — и это ровно то, что делает
демо честным: мы не продаём полторы секунды как решающие.

Выбытие инженера посреди дня. Случайный инженер с незакрытой работой
исчезает до конца дня; сравнение с тем же днём, где он на месте, и с той
же бригадой, которая едет по прежнему плану.

| Момент | Визитов у него | Как ехали | Пересчёт | Разница |
|---|---|---|---|---|
| 10:00 | 5,7 | 47,3 | 52,1 | **+4,8 ± 0,9** |
| 13:00 | 3,4 | 47,3 | 52,5 | **+5,2 ± 1,6** |
| 16:00 | 1,6 | 49,5 | 50,0 | +0,5 ± 0,3 |

Само выбытие стоит дню 5,2 визита при утреннем сроке; пересчёт возвращает
4,4 из них и оставляет 97% чужих визитов у прежних исполнителей. К вечеру
компенсировать уже нечего: в 16:00 потеря −1,0 визита остаётся −1,0 и с
пересчётом. Прирост в этот час (+0,5) даёт не спасение выбывшего, а
обычная переоптимизация остатка — эти два эффекта в замере разделены.

А вот прокол колеса на 40 минут оказался не событием вовсе: **он стоит дню
0,4–0,5 визита**, потому что буферы в маршруте его и так съедают. Из этой
потери пересчёт возвращает 0,1–0,7 визита. Кнопка при этом покажет
внушительные +1,1…+3,3 — но это не спасение от прокола, а обычная
переоптимизация остатка, которую можно было сделать и без всякого ЧП;
в замере эти два эффекта разделены нарочно. Различать «инженер
задержался» и «инженера сегодня не будет» важнее, чем пересчитывать в
обоих случаях: система, перетасовывающая бригаду из-за сорокаминутной
задержки, хуже той, что не делает ничего.

Равномерность загрузки выравнивается бесплатно. Джини по занятости
падает с 0,089 до 0,059, разрыв между самым и наименее занятым — с 57 до
29 пунктов, инженеров без единого визита не остаётся вовсе; покрытие при
этом не меняется (+0,1 ± 0,6 п.п. — интервал включает ноль). На утренних
сменах эффект впятеро сильнее: Джини 0,251 → 0,100, и покрытие там даже
растёт (+0,8 ± 0,4).

Но главную часть неравномерности лечит не алгоритм. При утренних сменах
двое установщиков не получают ни одной заявки — весь неразмещённый спрос
в такие дни открывается после 17:00, и человеку со сменой до 17:00 взять
его нечем. Расписание само по себе снижает Джини с 0,251 до 0,089, штраф
добивает до 0,059.

Подбор смен идёт в два этапа. Прокси размазывает спрос по окнам заявок и
считает непокрытие — оценка за доли миллисекунды, корреляция с настоящим
покрытием −0,93. Затем доводка: локальный подъём с оценкой настоящим
солвером, потому что прокси не знает географии и недобирает около трёх
пунктов (+4,5, причём выигрыш переносится на независимые прогоны
симуляции — то есть он настоящий, а не подгонка под конкретные случайные
числа).

Сам по себе прокси ручной веер не обыгрывает (+0,4 ± 1,1 — интервал
включает ноль), и это честнее, чем звучало бы «автоподбор лучше руками».
Обыгрывает связка: доводка добавляет +1,4 ± 0,9 сверх прокси, выводит на
+1,8 ± 1,5 против ручного веера и на +13,9 ± 1,9 против исходного
расписания.

## Другие размеры дня

Все основные замеры сделаны на одной конфигурации — 80 заявок,
12 инженеров. `stress` проверяет, что выводы не были её свойством.

| Заявок / инженеров | Жадный | Улучшенный | Разница | Итераций/с |
|---|---|---|---|---|
| 20 / 3 | 31,1% | 32,7% | +1,5 | 1789 |
| 40 / 6 | 49,6% | 58,5% | +8,9 | 359 |
| 80 / 12 | 62,3% | 67,6% | +5,3 | 191 |
| 120 / 18 | 60,0% | 66,9% | +6,9 | 123 |
| 150 / 22 | 62,3% | 68,2% | +5,8 | 94 |
| 240 / 36 | 62,1% | 69,2% | +7,1 | 46 |

Преимущество держится везде, инварианты чисты на всех конфигурациях,
включая вырожденные (один инженер, одна заявка, бригада больше числа
заявок). Скорость поиска падает примерно как n^1.3: на 240 заявках
остаётся 46 итераций в секунду, то есть около 370 шагов за
восьмисекундный бюджет. По таблице сходимости плато начинается после
двухсот — то есть на 240 заявках запас уже почти исчерпан. Если
настоящих заявок окажется заметно больше, бюджет надо поднимать.

При перекосе по загрузке (те же 80 заявок, бригада от 6 до 24 человек)
выигрыш тоже держится: от +5,1 до +7,6 пункта. Заметно другое: чем
свободнее бригада, тем неравномернее загрузка — при 24 инженерах Джини
0,58 просто потому, что работы на всех не хватает.

## Подстановка настоящих данных

С 15 сентября генератор заменяется на реальный набор заявок. Менять надо
только `core/generate.py` — он обязан вернуть `Day` с заполненными
`Order` и `Engineer`. Солвер и симулятор трогать не нужно. Вероятности
неявки и разброс длительностей в `WorkType` при переходе на реальные
данные оцениваются по истории выполнения.
